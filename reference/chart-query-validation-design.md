# 차트 쿼리 라벨 검사 보완 설계

이슈 #55의 목표는 Superset 6.1.0 프런트엔드가 지표를 조용히 제거하는 설정을 적용 전에 찾아내고, 원본 차트의 라벨 검사 범위를 명시하는 것이다. 아래 오류 정책과 지원 후보는 구현 전 설계다. 실측 결과를 계약에 반영한 뒤 코드와 테스트를 맞춘다. [이슈 #55](https://github.com/ohyounjo/dashboard/issues/55) · [PR #31](https://github.com/ohyounjo/dashboard/pull/31)

## 현재 동작

`load_project()`의 참조 검사가 차트 레지스트리의 `label_conflicts()`를 호출한다. 같은 쿼리 안에서 프런트엔드가 합치는 열과 지표를 먼저 빼고, 남은 항목이 서버에서 같은 라벨을 쓰면 오류를 모아 `ConfigError`로 보고한다. 기존 실측에서 `bar`는 같은 라벨의 서로 다른 adhoc SQL 지표와, adhoc 라벨이 저장 지표 이름과 같은 조합에서 첫 지표만 보냈다. 두 번째 지표가 없어져도 서버 응답은 성공이었다. 현재 검사는 hook이 있는 원본 `table`과 미등록 원본 유형을 건너뛴다. [기존 실측 및 규칙](../contracts/superset-notes.md#14-중복-열지표-라벨duplicate-columnmetric-labels) · [현재 계약](../contracts/chart-shorthand.md#중복-라벨-검사)

## 판정 정책

| 한 쿼리 안의 사례 | 제안 |
|---|---|
| 같은 이름의 저장 지표 반복, 또는 같은 라벨과 동일한 정의의 adhoc 지표 반복 | 실측에서 동일 항목을 하나로 합치는 경우 허용한다. |
| 같은 프런트엔드 제거 키를 가진 서로 다른 adhoc 정의, 또는 adhoc 지표와 저장 지표 | 서로 다른 항목을 제거하는 것으로 확인되면 설정 오류로 처리한다. 두 입력 순서를 검증한다. |
| 제거 뒤에도 열 이름과 지표 라벨이 겹치거나, 다른 저장 지표의 표시 이름이 겹침 | 기존 `Duplicate column/metric labels` 오류 경로와 문구를 유지한다. |
| `mixed`의 A와 B에 같은 라벨이 각각 한 번 나옴 | 실측대로 별도 쿼리이므로 허용한다. 각 묶음 안의 충돌은 독립적으로 검사한다. |

프런트엔드의 제거 키와 서버 라벨을 따로 계산한다. 저장 지표의 제거 키는 참조 이름이고, 서버 라벨은 기존 계약에 따라 데이터셋 `labels`의 표시 이름 또는 참조 이름이다. 열의 서버 라벨에는 표시 이름을 적용하지 않는다. adhoc 정의의 동일성은 Superset으로 전달되는 표현을 기준으로 본다. 축약 `{sql, label}`과 원본 SQL 객체의 표현 차이는 변환 결과로 판단하고, SQL 식 문자열 자체를 비교한다. SQL 의미나 공백·대소문자의 동등성은 추론 범위 밖이다. 원본 SIMPLE의 비교 필드, 라벨 생략 시 키, 확인 범위를 벗어난 객체의 취급은 6.1.0 빌더의 관측 결과로 확정한다.

새 오류도 기존 사용자 경로를 따른다. 예를 들어 두 SQL 식이 같은 라벨 `건수`를 쓰면 다음과 같이 수정 위치와 이유를 함께 보인다.

```text
dashboard.yaml:dashboards.main.charts[1].metrics[1]: 지표 라벨 '건수'로 서로 다른 지표가 겹침(metrics[0], metrics[1]). Superset이 첫 지표만 보내므로 각 지표에 고유한 라벨을 쓰세요.
```

오류 위치는 제거되는 첫 상이 항목의 실제 YAML 경로를 사용하고 메시지에 먼저 남는 항목도 표시한다. `params`에서 온 값이라면 `params.metrics[1]`처럼 찍는다. 같은 쿼리에서 서버 라벨 충돌도 남으면 원인이 다른 오류로 보고한다. CLI와 Studio 및 관리 서비스의 기존 오류 전달 경로를 재사용한다.

## 원본 차트 검사 범위

| 유형 | 확인할 입력과 지원 기준 |
|---|---|
| 레지스트리에 `viz_type`이 하나만 있고 hook이 없는 유형 | 현재의 원본 파라미터 매핑을 유지한다. `echarts_timeseries_bar`, `pie`, `mixed_timeseries`를 회귀 대상으로 둔다. |
| `table` | 행 모드에서 `all_columns`, 집계 모드에서 `groupby`와 `metrics`를 우선 확인한다. 두 모드의 열 병합, 반대 모드 필드의 무시 여부, `query_mode` 생략 시 동작, `percent_metrics`와 정렬 옵션이 실제 쿼리에 주는 영향을 확인해 모드별 지원 범위를 적는다. 축약 `table`의 최종 `params`에도 같은 모드 판정을 적용한다. |
| 갤러리 원본 `graph_chart`, `tree_chart`, `gantt_chart` | 갤러리에서 쓰는 입력을 기준으로 각각 `source/target/metric`, `id/parent/name/metric`, `start_time/end_time/y_axis/series`가 실제 payload의 어느 쿼리에 들어가는지 확인한다. 정상·충돌 사례로 쿼리와 제거 규칙을 재현한 형태만 검사에 추가한다. |
| 카탈로그의 `chord`, `world_map`, `country_map` | 기존에 기록된 관리자용 조회 경로와 실제 요청 구조를 표에 기록한다. 기본 guest 역할에서의 렌더링 한계를 유지한다. 같은 라벨 검사를 적용할 근거가 부족한 경우 미지원으로 표시한다. |
| 그 밖의 원본 유형, 여러 레지스트리 항목에 매핑되는 유형, 확인 범위 밖의 설정 | 라벨 검사 미지원 상태에서 기존 원본 설정의 호환성을 유지한다. 계약의 적용 범위 표에 명시한다. `make check` 통과로 보장하는 범위는 지원된 모드의 정적 검사까지다. |

## 실측과 구현 순서

1. 기존 개발 스택과 분리된 Superset 6.1.0 테스트 스택에서 갤러리의 데이터와 스키마를 사용한다. 후보 설정을 검증하기 전에 기존 동작을 재현한다. 변경 후 검증이 거부할 사례는 테스트 스택의 Superset 차트 폼에서 만들거나 테스트 스택에만 직접 import한다.
2. 대시보드 화면이 만든 요청에서 조회 경로, 쿼리별 `columns`·`metrics`와 순서, 응답 상태, 차트 결과를 유형·모드·사례별로 기록한다. 같은 adhoc 라벨의 동일 SQL과 다른 SQL, 저장 지표 이름과 adhoc 라벨이 같은 두 순서, 표시 이름 충돌을 포함한다. 원본 유형은 정상·중복 열·열과 지표 라벨 충돌을 해당 필드가 있는 범위에서 확인한다. 현재 `tests/test_gallery.py`의 직접 API 호출은 프런트엔드의 제거 동작을 검증하는 근거로 사용할 수 없다.
3. `dashkit/charts/__init__.py`의 값 추출과 `label_conflicts()`를 확장한다. 축약 파라미터 변환과 `params`의 얕은 덮어쓰기 순서를 번들 생성과 맞추면서 각 값의 YAML 경로를 보존한다. `params`가 지원되는 `viz_type`으로 덮는 경우에는 실제 번들이 보내는 유형과 파라미터로 검사하고, 미지원 유형은 위 표의 기준을 따른다. `table`의 모드별 파라미터를 기존 hook의 출력과 대조한다. 쿼리 경계와 열 병합은 레지스트리 선언을 재사용하고, 필요한 원본 유형만 그에 맞는 매핑을 추가한다.
4. `contracts/superset-notes.md` 14절에는 새 실측의 환경과 표를, `contracts/chart-shorthand.md`에는 오류 규칙과 원본 유형별 지원 표를 적는다. `contracts/README.md`의 참조 검사 표와 `reference/chart-catalog.md`의 원본 유형 안내를 맞춘다. 생성되는 차트 표가 달라지면 `make gen`으로 갱신한다.
