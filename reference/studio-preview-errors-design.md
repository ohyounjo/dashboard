# Studio 미리보기 적용 중 오류 및 서비스워커 조사 설계

관련 이슈: [#51](https://github.com/ohyounjo/dashboard/issues/51), 선행 관찰: [PR #30](https://github.com/ohyounjo/dashboard/pull/30). 이 문서는 조사와 조건부 수정의 계획이며 재현 결과가 아니다.

## 목표와 현재 근거

격리된 스택에서 `service-worker.js` 404, 적용 중 차트 400/404, 로그인 전 401, 화면 이동으로 취소된 요청을 각각 재현하고 사용자에게 보이는 영향과 실제 결함을 판별한다. 결함이 확인된 경우에만 원인을 수정한다. 단순히 콘솔이나 네트워크 오류를 감추는 것은 해결이 아니다.

PR #30에서 서비스워커 404가 관찰됐고 이전 검사에서 차트 400/404가 일시적으로 관찰됐다. 요청 URL, 개시자와 실제 영향은 아직 확인되지 않았다. 저장소의 `web/studio/app.js`에서 `finishApply`는 성공일 때만 `reloadPreview()`를 호출하지만, 기존 미리보기 iframe은 적용 중에도 유지된다. 따라서 기존 화면의 요청과 sync의 변경이 겹칠 가능성은 조사 가설이며 확인된 원인이 아니다. 저장소의 Superset 설정·웹 코드에서 서비스워커 등록을 발견하지 못했으므로 이미지 내부 코드, 응답과 브라우저 상태까지 추적한다.

## 지켜야 할 계약

- `contracts/studio.md`: Studio는 로컬 전용이고 미리보기는 Studio → 웹앱 → Superset의 중첩 iframe이다. 웹앱은 마지막 sync 성공 프로젝트를 보여 준다. 적용 성공 시 새로 고침하며, 실패 시 오류와 로그를 보여 준다. 스트림 단절 시 상태 조회로 결과를 복구한다.
- `contracts/api.md`: `embed.json`의 마지막 sync 성공 프로젝트가 현재 프로젝트다. load 성공 후 sync 실패 시 DB와 이전 설정이 어긋날 수 있으며 이를 성공으로 표시하지 않는다.
- `contracts/auth.md`와 `contracts/studio.md`: 로그인, guest token, SameSite 쿠키, Host/Origin 검사, 프레임 허용 및 CSP를 유지한다. 읽기 경로는 `dash_reader` 또는 `dash_inspect`만 사용한다. 서비스워커를 위해 정책을 느슨하게 만들거나 관리자 권한을 부여하지 않는다.
- 390px에서는 기본적으로 미리보기가 접힌다. 접힌 상태의 Studio와 별도 창 웹앱을 검사하고, 미리보기를 수동으로 연 경우도 확인한다. 다른 출처에서는 기존 안내가 유지돼야 한다.

## 격리 및 증거 수집

별도 작업 폴더에서 `make info`로 테스트 이름과 포트를 확인하고 `KEEP=1 make test`의 테스트 스택을 사용한다. `Makefile`의 `TEST_ENV`와 `_test_run`을 확인해 동일한 테스트 프로젝트명·포트·`.test/state`, `.test/build` 및 `STUDIO_ORIGIN`으로 Studio를 기동한다. 테스트 프로젝트의 파일과 볼륨만 수정하며 개발 데이터·상태를 건드리지 않는다. 테스트 종료 시 해당 스택만 `make test-down`으로 정리한다. 비밀값, 쿠키, 토큰, 사용자 데이터가 기록물에 남지 않도록 한다.

브라우저와 Superset 이미지 버전, 정확한 출처와 경로, 새 프로필 여부, 시간 및 적용 로그의 check/load/sync·import/embed/prune·done 순서를 기록한다. DevTools 또는 자동화로 프레임별 요청 URL·메서드·상태·개시자·요청/응답 시각·취소 이유와 화면 증상을 대응한다. 민감한 헤더·본문은 저장하지 않는다. 네트워크 실패와 HTTP 응답을 구별하고, 동일 조건을 반복한 횟수와 재현 여부를 남긴다. 재현하지 못한 현상은 원인 확정이나 통과로 취급하지 않는다.

| 사례 | 재현과 대조 | 판정에 필요한 증거 |
| --- | --- | --- |
| 서비스워커 404 | 깨끗한 브라우저 프로필에서 웹앱과 중첩 Superset을 열고, 기존 등록이 있는 프로필과 비교한다. 이미지 내부 등록 코드, 실제 경로·응답 및 프록시/배포 설정을 확인한다. | 어느 프레임이 등록했는지, 스코프와 제공 파일의 유무, 등록 실패 및 사용자 기능 영향. 기존 등록 잔재와 현재 배포의 문제 구분 |
| 차트 400/404 | 서로 다른 프로젝트 적용과 같은 프로젝트 재적용을 반복한다. 차트가 남고 삭제·교체되는 구성을 테스트 사본에서 준비하고 sync 단계 중 기존 iframe의 요청과 완료 후 새 요청을 비교한다. 수동 새로고침과 적용 직후 전환도 확인한다. | 실제 요청·응답 및 대상 차트 ID와 sync 로그 시간, 화면 오류가 지속되는지, 적용 완료 후 새 프로젝트가 회복되는지. 400과 404는 따로 분석 |
| 로그인 전 401 | 새 세션에서 로그인 전후 같은 경로를 비교한다. | 인증 확인용 예상 응답인지, 로그인 화면 및 로그인 후 접근에 문제가 있는지 |
| 취소 요청 | 화면 이동 또는 iframe 새로고침 전후 요청을 비교한다. | 브라우저 취소와 서버 오류의 구분, 최종 화면의 정상 여부 |

## 수정 결정과 경계

서비스워커 문제가 현재 배포의 결함이면 등록 URL, 제공 정적 파일과 프록시 경로 중 실제 원인을 수정한다. 기능상 필요 없는 등록의 제거는 해당 이미지/버전의 동작과 부작용을 확인한 뒤 결정한다. 빈 성공 응답, 무조건적인 404 가리기, 무관한 캐시 초기화는 해결책으로 삼지 않는다. 기존 등록에만 원인이 있으면 안전한 재현 및 복구 방법과 남는 영향을 기록한다.

차트 결함이면 실측한 경쟁 구간을 없애거나 사용자가 명확히 이해하고 복구할 수 있게 한다. 예를 들어 적용 중 기존 프레임의 요청이 원인일 때에만 적용 시작부터 미리보기를 안전하게 일시 중지하고 성공 시 현재 프로젝트를 다시 로드하는 방안을 검토한다. 이 방식은 iframe을 제거할 때 로그인 상태, 수동 접기, 프로젝트 전환, 접근성 및 불필요한 재생성이 영향을 받을 수 있으므로 검증한다. 실패·스트림 단절·재접속·중복 적용·수동 새로고침도 다룬다. 실패 후 이전 설정과 DB의 불일치를 숨기지 않으며, 실패 단계에 맞는 기존 안내를 유지한다. 401이나 탐색 취소가 정상이라도 기록하고 기능이나 보안 검사를 우회하지 않는다.

동작 변경이 확정되면 `contracts/studio.md` 등 해당 계약을 실측 결과에 맞게 갱신한다. 계약과 이슈가 충돌하면 기존 계약을 기준으로 차이를 이슈에 알리고 범위나 완료 조건이 바뀌면 이슈를 갱신한다.

## 검증과 완료 기준

- 각 요청에 대해 재현 조건, 응답 또는 취소, 발생 단계, 화면 영향, 정상/결함 판단과 근거를 남긴다. 재현 불가에는 시도 조건과 한계를 적는다.
- 실제 결함에 대한 회귀 테스트는 원인에 맞는 수준에서 추가한다. 적용 성공·실패, sync 실패, 스트림 단절 후 복구, 적용 중 조작과 프로젝트 전환을 다루고 정상 401/취소를 오류 억제 테스트로 대체하지 않는다. 서비스워커 경로 변경 시 실제 배포 경로·응답을 검증한다.
- 1280px·390px 각각 라이트/다크에서 Studio, 로그인, 적용 및 적용 후 차트를 확인한다. 390px 기본 접힘과 수동 펼침, 다른 출처 안내도 확인한다. 성공·실패와 상태 복구 시 사용자에게 보이는 결과를 남긴다.
- 권한 없는 접근과 guest token 경계, Studio Host/Origin 보호, 중첩 iframe의 CSP 및 로그인 쿠키를 검증한다. `make test-unit`, 격리된 `make test`, `git diff --check`를 실행하고 미실행 사유를 기록한다.
- 재현 증거, 변경과 남은 제약을 구현 PR에 기록한다. 미해결 완료 조건이 있으면 draft로 명확히 남긴다.
