# 보강 구현 오케스트레이션 프롬프트 (무인 실행용)

새 Claude Code 세션을 이 저장소 폴더에서 열고 아래 블록 전체를 붙여 넣는다.
범위를 줄이려면 `# 범위`의 단계 목록에서 뒤쪽 단계를 지운다.

````text
# 역할
너는 이 저장소의 보강 작업 오케스트레이터다. 나는 자리를 비운다. 질문하지 말고 끝까지 진행한다.
설계는 reference/enhancement-plan.md에 있고 7절의 결정은 확정이다. 다시 논의하지 않는다.
판단이 필요한 곳은 설계서의 의도에 가장 가까운 쪽으로 정하고, 정한 내용과 이유를 PR 본문과 최종 보고에 적는다.

# 먼저 읽을 것
- reference/enhancement-plan.md: 구현할 내용(3~6절), 결정(7절), 단계와 완료 조건(8절), 하지 않는 것(9절)
- reference/chart-catalog.md: 차트 유형별 Superset 이름과 파라미터
- AGENTS.md: 프로젝트 규칙과 리뷰 기준
- contracts/: 구현이 따라야 하는 계약. 동작을 바꾸면 계약 문서도 같은 PR에서 고친다
- done.md: 지금 구현의 한계

# 범위
아래 단계를 순서대로 진행한다. 단계 하나가 PR 하나다. 앞 단계가 main에 병합된 뒤에 다음 단계를 시작한다.
- 준비: 로컬 브랜치 docs/enhancement-plan(설계 문서만 있음)을 푸시하고 PR을 올려 아래 "PR 절차"대로 병합한다
- 0단계: 안전망 (3-1 스냅샷 테스트, 3-2 테스트 분리와 별도 테스트 스택, 3-3 CI)
- 1단계: 차트 유형 레지스트리로 기존 6종 이전 (4-1)
- 2단계: 축약 유형 추가, 갤러리 프로젝트, Superset 버전 관리 (4-1, 4-5, 3-4)
- 3단계: 위젯 매니페스트, 배치·필터 확장, prune 표식 (4-2, 4-3, 3-5)
- 4단계: make new, make plan, 설정 버전 (5-1, 5-2, 5-3)
- 5a단계: Studio 프로젝트 마법사, 데이터 교체, 탭 구성 (6절)
- 5b단계: Studio 대시보드 배치, 필터 (6절)
6단계(8절 표의 마지막 줄)는 하지 않는다.

# 단계마다 하는 일
1. main을 최신으로 받고 브랜치를 만든다. 이름은 기존 방식대로 feat/…, chore/…, docs/….
2. 설계서의 해당 절을 구현한다. 서로 독립적인 작업은 서브에이전트에 병렬로 맡기고, 너는 계약과 통합을 맡는다.
3. 설계서에 "실측 필요", "확인한 뒤 구현"이라고 적힌 항목은 실행 중인 Superset 6.1.0에서 먼저 확인하고 결과를 contracts/superset-notes.md에 남긴다.
   실측이 통과하지 못하면 설계서에 적힌 대안을 따른다(예: 7절 D3, D4의 조건).
4. 8절 표의 그 단계 완료 조건을 테스트로 확인한다. make test-unit(0단계 이후)과 make test가 모두 통과해야 한다.
5. "PR 절차"를 따른다.

# 구현 규칙
- 호스트에는 Docker와 make만 있다고 가정한다. 파이썬 작업은 tools 컨테이너에서 실행한다.
- 새 의존성은 설계서에 이름이 있는 것만 추가한다(ruamel.yaml은 Studio 빌드 단계에만). 모든 버전을 정확히 고정한다.
- 기존 두 예시 프로젝트(devtracker, sales-sample)의 설정 파일은 고치지 않아도 통과해야 한다. 고쳐야만 한다면 그 단계를 멈추고 "멈추는 조건"을 따른다.
- 템플릿 코드(dashkit/, web/, superset/)에 예시 도메인 단어를 넣지 않는다. tests/test_domain_words.py가 계속 통과해야 한다.
- 권한 경계를 지킨다: 읽기 경로는 reader 계정만, backend에는 Superset 계정이 없다. Studio는 별도 컨테이너(compose studio 프로필, 127.0.0.1 전용)다.
- 비밀값은 코드와 커밋에 넣지 않는다. 타입 힌트를 유지한다.
- 실패한 테스트를 건너뛰거나 지우거나 기대값을 느슨하게 바꿔서 통과시키지 않는다.
- 개발 스택(웹앱 8080, Superset 8088)은 내가 쓰던 상태(PROJECT=devtracker)로 남겨 둔다. 테스트로 바꿨다면 되돌린다.
- UI를 바꾼 단계는 헤드리스 브라우저로 화면을 직접 확인한다. 라이트·다크, 1280px·390px.

# PR 절차
1. 커밋하고 푸시한 뒤 gh pr create로 PR을 올린다. .github/pull_request_template.md 형식을 채운다.
   - UI 변경이 없으면 "UI 변경 없음"이라고 쓴다. 있으면 변경 전·후 화면 캡처를 넣는다.
   - 본문에 설계서의 어느 절을 구현했는지, 완료 조건의 확인 결과(테스트 출력 요약), 스스로 정한 판단을 쓴다.
2. 리뷰를 기다린다. 리뷰어는 Codex(chatgpt-codex-connector[bot])이고 보통 PR을 올리고 몇 분 안에 요약 댓글과 줄 단위 댓글을 단다.
   - gh pr view, gh api repos/ohyounjo/dashboard/pulls/<번호>/comments 로 확인한다. 2분 간격으로 최대 20분 기다린다.
   - GitHub Actions 검사(화면 캡처 등)가 돌면 끝날 때까지 기다린다.
3. 리뷰 댓글을 처리한다.
   - P0, P1: 반드시 고친다.
   - P2: 타당하면 고친다. 고치지 않으면 이유를 그 댓글에 답글로 남긴다.
   - 지적이 틀렸다고 판단하면 근거(코드 위치, 테스트 결과)를 답글로 남기고 고치지 않는다.
   - 고친 것은 테스트를 다시 돌린 뒤 새 커밋으로 푸시하고(강제 푸시 금지), 각 댓글에 반영한 커밋 해시와 내용을 한국어로 답글로 남긴다.
4. 푸시한 뒤 다시 2번으로 돌아가 재리뷰를 기다린다(최대 10분). 이 반복은 PR당 최대 3번이다.
5. 아래를 모두 만족하면 gh pr merge --merge로 병합하고 브랜치를 지운다.
   - 처리되지 않은 P0, P1 지적이 없다
   - make test-unit과 make test가 마지막 커밋에서 통과했다
   - GitHub Actions 검사에 실패가 없다
   - 20분 안에 리뷰가 달리지 않았다면: 위 두 조건을 만족할 때 병합하고, PR에 "리뷰 없이 병합함"이라고 댓글을 남긴다
6. 병합 뒤 main을 받아 make up && make apply가 되는지 확인하고 다음 단계로 간다.

# 멈추는 조건
아래 경우에는 그 단계에서 멈추고, 뒤 단계를 시작하지 않는다. PR은 열어 둔 채(또는 draft로) 상황을 댓글로 남긴다.
- 리뷰 반복 3번 뒤에도 P0 또는 P1이 남았다
- 테스트를 통과시킬 수 없다
- 완료 조건을 만족하려면 설계서의 결정(7절)이나 "하지 않는 것"(9절)을 어겨야 한다
- 기존 예시 프로젝트 설정을 고쳐야만 한다
- 데이터를 지우는 작업(make reset, 볼륨 삭제, 강제 푸시, main 직접 푸시)이 필요하다. 이런 작업은 하지 않는다

# 금지
- main에 직접 커밋하거나 푸시하지 않는다. 강제 푸시하지 않는다.
- 이 저장소(ohyounjo/dashboard) 밖의 외부 서비스에 올리거나 배포하지 않는다.
- .env와 비밀값을 PR, 댓글, 로그에 쓰지 않는다.
- 내 개발 스택의 볼륨과 .state/를 지우지 않는다.

# 최종 보고
끝나거나 멈추면 reference/enhancement-report.md를 쓰고(마지막 PR에 포함하거나, 멈췄다면 그 브랜치에 커밋) 같은 내용을 마지막 메시지로 남긴다.
- 단계별 상태: 병합됨 / 멈춤 / 시작 안 함, PR 링크
- 단계별 완료 조건의 확인 결과(테스트 출력 요약)
- 리뷰에서 받은 지적과 처리(고침 / 고치지 않음과 이유)
- 실측 결과와 그에 따라 설계서와 달라진 점
- 스스로 정한 판단 목록
- 남은 한계와 내가 직접 확인해야 할 것(특히 화면)
````
