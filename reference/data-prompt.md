# 데이터 추가 적재·테이블 관리 구현 오케스트레이션 프롬프트 (무인 실행용)

새 Claude Code 세션을 이 저장소 폴더에서 열고 아래 블록 전체를 붙여 넣는다.
범위를 줄이려면 `# 범위`의 단계 목록에서 뒤쪽 단계를 지운다.

**기본 범위는 1~4단계(핵심)다.** 설계서 13절 D7(선택 기능은 처음에 넣지 않고 필요할 때 하나씩)에 따라 5단계(선택 기능)는 블록에 들어 있지 않다. 선택 기능을 넣을 때는 이 파일 맨 아래 "선택 기능을 넣을 때"를 따른다.

정해 둔 값(그대로 써도 된다. 바꾸려면 블록에서 고친다):

- 리뷰 반복 횟수. 블록의 `PR당 최대 8번`은 설계서 PR에서 리뷰가 19번 돈 경험으로 넉넉히 잡은 값이다. 줄이려면 그 숫자를 바꾼다.
- 한도 값(파일 200MB·200만 행 등)은 가정한 값이다. 1단계에서 실측하고, 블록의 "멈추는 조건"에 적은 기준을 넘으면 거기서 멈춘다. 실제 데이터 크기를 알고 있으면 그 기준을 고친다.

2. 계약을 먼저 고친다. contracts/ingest.md, contracts/manage.md(1단계에서 새로 쓰고 이후 단계에서 채운다)와 설계서 12절이 적은 문서

# 구현 규칙
원칙(테스트로 고정한다. 어기는 구현은 병합하지 않는다):
- 원본은 파일이다. 누적 테이블의 내용은 (schema.yaml, 번호순 배치 파일들)만으로 정해지고 DB는 그 결과물이다.
  빈 DB에 make apply하면 운영 중에 하나씩 더해 만든 것과 같은 행이 나와야 한다(5-7). 정책 셋 모두, 빠른 취소·되돌리기·합치기 뒤에도.
- 운영 중의 추가 적재와 load의 다시 만들기는 같은 함수(apply_batch)를 쓴다. 경로를 둘로 만들지 않는다.
- 배치 폴더에는 정규형만 둔다. 머리글에는 그 배치가 실제로 받은 열만 남기고 빠진 열을 채워 넣지 않는다(4-2, 5-5).
  같은 행들을 폼·붙여넣기·파일로 넣은 배치 파일이 바이트 단위로 같아야 한다.
- 폴더나 raw를 바꾸는 작업(더하기, 빠른 취소, 되돌리기·되살리기, 합치기, 구조 변경)은 모두 10-3의 공통 순서를 지키고,
  그 순서는 함수 하나가 감싼다. 작업마다 따로 구현하지 않는다.
- 쓰기 잠금은 데이터 DB에 하나다(세션 단위 advisory lock). 잠금 밖에서는 올린 내용만 보고 정해지는 일만 하고,
  DB나 폴더의 상태를 보고 정하는 일(프로젝트 확인, 설정 대조, 복구, 파일 대조, 중복 확인, 참조 대조, 비교, 반영, checks, 확정)은 모두 잠금 안에서 한다.
- 파일을 지워도 되는지를 판정하는 곳은 복구 절차 하나뿐이다. 커밋에 실패했거나 결과를 받지 못한 작업은 직접 치우지 않는다.
- Studio와 manager는 라우팅과 권한만 갖는다. 로직은 dashkit/project/와 dashkit/ingest/에 한 벌만 둔다.
  같은 연산을 두 API로 실행했을 때 쓰인 파일이 바이트 단위로 같다는 테스트를 둔다.
- 등록 표로 만든다: PARSERS, NORMALIZERS, POLICIES, 운용 메뉴 모듈, web/shared/fields.js. 종류를 더할 때 if 사슬이 늘면 안 된다.

경계:
- DB 계정: 대시보드 데이터 읽기는 dash_reader만, 인증·감사 로그는 dash_auth만, manager의 읽기 경로(조회·목록)는 dash_inspect만 쓴다.
  owner 연결은 쓰기 작업에서만 연다. backend에는 owner 계정과 Superset 계정을 주지 않는다.
  dash_reader가 raw를 읽지 못하고, dash_inspect가 쓰지 못하고 dashkit_auth를 읽지 못한다는 것을 테스트로 고정한다.
- 새 DB 스키마를 만들지 않는다(raw, dash, dashkit_meta 셋 그대로). 새 파이썬 의존성을 추가하지 않는다.
- replace 테이블의 적재 경로와 값 검증의 엄격함은 건드리지 않는다. 번들 스냅샷(tests/golden/)과 기존 로더·Studio 테스트가 그대로 통과해야 한다.
  기대값을 느슨하게 바꾸거나 테스트를 건너뛰거나 지우지 않는다.
- 기존 예시 프로젝트(devtracker, sales-sample, chart-gallery)의 설정 파일과 CSV는 고치지 않는다. 누적 테이블의 예시가 필요하면 tests/fixtures/에 둔다.
- 템플릿 코드(dashkit/, web/, superset/)에 예시 도메인 단어를 넣지 않는다. tests/test_domain_words.py가 새 폴더를 포함해 계속 통과해야 한다.
- 권한 검사는 서버에서 한다. 10-4의 표(operator는 조회·더하기·자기 배치 되돌리기, admin은 구조 변경·삭제·합치기·토큰)마다 테스트를 둔다.
- 사용자 입력이 들어가는 SQL은 전부 매개변수 바인딩이고 식별자는 목록과 대조한 뒤 psycopg.sql.Identifier로만 넣는다.
- 비밀값은 코드와 커밋에 넣지 않고 환경변수로만 받는다. 로그·오류 응답·감사 로그에 비밀값과 데이터 값을 싣지 않는다.
- 타입 힌트를 유지한다.

방법:
- 호스트에는 Docker와 make만 있다고 가정한다. 파이썬 작업은 tools 컨테이너에서 실행한다.
- "죽인 뒤 복구" 테스트는 프로세스를 실제로 죽이지 않고, 공통 순서의 단계 사이에 실패를 끼워 넣을 수 있는 자리(테스트 전용)를 두어 만든다.
  묶음 기록의 상태마다(5-4의 ①②③, 합치기 6-4, 구조 변경 6-3) 하나씩 둔다.
- 1단계의 실측: 테스트 스택에서 임시 프로젝트로 100만 행을 만들어 apply 시간, 한 배치 추가의 잠금 구간 시간, 배치 200개일 때의 apply 시간을 잰다.
  결과를 reference/data-design.md 15절에 적고 13절 D8의 한도를 그에 맞게 고친다(같은 PR). 만든 데이터 파일은 커밋하지 않는다.
- 화면은 기존 방식을 따른다: 바닐라 JS, 빌드 단계 없음, 문구는 web/strings.js, 인라인 스크립트 없음(CSP), 기존 디자인 토큰.
  입력 폼은 schema.yaml에서 만들고 테이블마다 화면 코드를 쓰지 않는다.
- UI를 바꾼 단계는 헤드리스 브라우저로 화면을 직접 확인한다. 라이트·다크, 1280px·390px. 직접 입력은 키보드만으로 끝까지 되는지 본다.
  e2e 화면 캡처(e2e/, .github/workflows/ui-screenshots.yml)에 새 화면을 더한다.
- 개발 스택(웹앱 8080, Superset 8088)은 내가 쓰던 상태(PROJECT=devtracker)로 남겨 둔다. 테스트는 테스트 스택(make test)에서 돌린다.
  1단계를 병합한 뒤에는 개발 스택에 make data-init을 실행해 둔다. 볼륨을 다시 만들지 않는다.
- manager는 compose의 manage 프로필이다. 포트를 밖에 열지 않고 nginx의 /api/manage/로만 닿게 한다.

# PR 절차
1. 커밋하고 푸시한 뒤 gh pr create로 PR을 올린다. .github/pull_request_template.md 형식을 채운다.
   - UI 변경이 없으면 "UI 변경 없음"이라고 쓴다. 있으면 변경 전·후 화면 캡처를 넣는다.
   - 본문에 설계서의 어느 절을 구현했는지, 완료 조건의 확인 결과(테스트 출력 요약), 스스로 정한 판단을 쓴다.
2. 리뷰를 기다린다. 리뷰어는 Codex(chatgpt-codex-connector[bot])이고 PR을 올리면 몇 분 안에 요약 댓글과 줄 단위 댓글을 단다.
   - gh pr view, gh api repos/ohyounjo/dashboard/pulls/<번호>/comments 로 확인한다. 20초 간격으로 최대 20분 기다린다.
   - 지적이 없으면 리뷰가 아니라 "Didn't find any major issues" 댓글이 달린다. 그것도 끝난 것으로 본다.
   - GitHub Actions 검사(tests, ui-screenshots)가 돌면 끝날 때까지 기다린다.
3. 리뷰 댓글을 처리한다.
   - 먼저 지적이 맞는지 코드와 설계서에 대조한다. 맞으면 고친다.
   - P0, P1: 반드시 고친다. 권한·DB 계정 경계·비밀값·데이터 유실에 관한 지적은 등급과 상관없이 P1로 다룬다.
   - P2: 타당하면 고친다. 고치지 않으면 이유를 그 댓글에 답글로 남긴다.
   - 지적이 틀렸다고 판단하면 근거(코드 위치, 테스트 결과)를 답글로 남기고 고치지 않는다.
   - 같은 뿌리의 지적이 되풀이되면 경로 하나씩 고치지 말고 규칙을 한 곳에 모은다(설계서 10-3의 공통 순서가 그렇게 만들어졌다).
   - 지적이 설계서의 빈 곳을 짚었으면 설계서와 계약도 같은 PR에서 고치고 3-3 표에 한 줄 적는다.
   - 고친 것은 테스트를 다시 돌린 뒤 새 커밋으로 푸시하고(강제 푸시 금지), 각 댓글에 반영한 커밋 해시와 내용을 한국어로 답글로 남긴다.
4. 푸시만으로는 Codex가 다시 리뷰하지 않는다. PR에 "@codex review" 댓글을 달아 재리뷰를 요청하고 2번으로 돌아간다.
   지적이 없어질 때까지 되풀이하되 PR당 최대 8번이다.
5. 아래를 모두 만족하면 gh pr merge --merge로 병합하고 브랜치를 지운다.
   - 처리되지 않은 P0, P1 지적이 없다(8번을 채웠다면 남은 P2는 답글로 이유를 남기고 최종 보고에 적는다)
   - make test-unit과 make test가 마지막 커밋에서 통과했다
   - GitHub Actions 검사에 실패가 없다
   - 20분 안에 리뷰가 달리지 않았다면: 위 두 조건을 만족할 때 병합하고, PR에 "리뷰 없이 병합함"이라고 댓글을 남긴다
6. 병합 뒤 main을 받아 개발 스택에서 make up && make apply가 되는지, 기존 화면이 그대로인지 확인하고 다음 단계로 간다.

# 멈추는 조건
아래 경우에는 그 단계에서 멈추고, 뒤 단계를 시작하지 않는다. PR은 열어 둔 채(또는 draft로) 상황을 댓글로 남긴다.
- 리뷰 반복 8번 뒤에도 P0 또는 P1이 남았다
- 테스트를 통과시킬 수 없다

- "빈 DB에 다시 만든 결과가 하나씩 더한 결과와 같다"(5-7)를 지킬 수 없는 경우를 찾았다
- 1단계의 실측에서 100만 행 프로젝트의 apply가 10분을 넘거나, 한 배치 추가의 잠금 구간이 10초를 넘는다
  (설계서 13절 D1의 대안을 다시 볼 사유다. 실측 결과를 설계서에 적은 1단계 PR까지만 올리고 멈춘다)

- 기존 예시 프로젝트의 설정이나 CSV, 번들 스냅샷을 고쳐야만 한다
- 데이터를 지우는 작업(make reset, 볼륨 삭제, 강제 푸시, main 직접 푸시)이 필요하다. 이런 작업은 하지 않는다.
  기존 data-db 볼륨에 dash_inspect 계정을 더하는 것은 make data-init으로 하고 볼륨을 다시 만들지 않는다

## 선택 기능을 넣을 때

1~4단계가 main에 병합된 뒤에 한다. 위 블록을 그대로 쓰되 세 군데를 고친다.

1. `# 범위`의 단계 목록을 아래 줄들로 **바꾼다**(준비와 1~4단계 줄은 지운다). 넣을 기능만 남긴다.
2. `# 범위` 끝의 "14절의 5단계(선택 기능 …)도 이번 범위가 아니다 … 넣지 않는다" 문장을 지운다.
3. `# 구현 규칙`의 "경계:"에 아래 "더하는 규칙"을 붙인다.

````text
- 5단계: 선택 기능. 기능 하나가 PR 하나다. 아래 순서로 한다.
  - 민감 열(schema.yaml의 sensitive 키. MANAGE_FEATURES가 아니다) (10-4)
  - SQL 콘솔(sql) (8-3)
  - 내보내기(export) (8-4)
  - 열 통계(profile) (9-1)
  - 신선도 표시(freshness) (9-3)
  - API 토큰(tokens) (10-5)
  - 표 차트 page_size: Superset에서 실측한 뒤 contracts/superset-notes.md에 적고 넣는다. 실측이 통과하지 않으면 넣지 않고 이유를 보고한다 (8-5)
````

더하는 규칙:

````text
- 선택 기능은 기본으로 꺼져 있다(MANAGE_FEATURES, 설계서 10-6). 꺼진 기능의 경로는 404이고 운용 화면은 GET /api/manage/config의 features로 메뉴를 그린다.
  민감 열만은 기능 스위치가 아니라 schema.yaml의 sensitive 키로 켠다(DB 권한이라 스위치와 따로 놀면 안 된다).
- 민감 열의 값은 운용 API의 어떤 응답에도 싣지 않는다. 설계서 10-4의 검증 조건 ①~⑨를 테스트로 고정한다.
  권한·민감 열에 관한 리뷰 지적은 등급과 상관없이 P1로 다룬다.
- SQL 콘솔은 dash_inspect + 읽기 전용 트랜잭션 + 시간 제한 + 감싸기(8-3)다. 콘솔로 쓰기와 dashkit_auth 읽기가 안 된다는 것을 테스트로 고정한다.
- API 토큰으로는 허용된 테이블에 데이터 더하기와 그 작업의 상태 보기만 된다. 조회·구조 변경이 안 된다는 것을 테스트로 고정한다.
- 선택 기능의 설정 키(sensitive, freshness)와 경로는 그 기능의 PR에서 계약(schema.schema.json, contracts/manage.md, contracts/api.md)에 함께 넣는다.
````
