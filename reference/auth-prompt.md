# 로그인·사용자 관리 구현 오케스트레이션 프롬프트 (무인 실행용)

새 Claude Code 세션을 이 저장소 폴더에서 열고 아래 블록 전체를 붙여 넣는다.
범위를 줄이려면 `# 범위`의 단계 목록에서 뒤쪽 단계를 지운다.

실행 전에 정할 것: 블록 안의 `<사내 도메인>`을 가입을 허용할 메일 도메인으로 바꾼다. 아직 정해지지 않았으면 `example.com`으로 두고 나중에 `.env`의 `AUTH_EMAIL_DOMAINS`만 바꾼다.

````text
# 역할
너는 이 저장소의 로그인·사용자 관리 구현 오케스트레이터다. 나는 자리를 비운다. 질문하지 말고 끝까지 진행한다.
설계는 reference/auth-design.md에 있고 2절의 기능 범위와 4-1의 접근 단위(탭)는 확정이다. 다시 논의하지 않는다.
판단이 필요한 곳은 설계서의 의도에 가장 가까운 쪽으로 정하고, 정한 내용과 이유를 PR 본문과 최종 보고에 적는다.

# 먼저 읽을 것
- reference/auth-design.md: 기능 범위(2절), 권한(3절), 접근 제어(4절), 계정 흐름(5절), 메일 테스트 모드(6절),
  보안(7절), 화면(8절), 통계와 기록(9절), 데이터 모델(10절), API(11절), 구성 변경(12절), 단계와 완료 조건(13절)
- AGENTS.md: 프로젝트 규칙과 리뷰 기준
- contracts/api.md, contracts/studio.md: 지금의 API 계약과 요청 보호 방식(dashkit/studio/guard.py)
- dashkit/api/app.py, dashkit/api/state.py, dashkit/db.py, web/app.js, web/nginx.conf.template, docker-compose.yml, .env.example

# 범위
아래 단계를 순서대로 진행한다. 단계 하나가 PR 하나다. 앞 단계가 main에 병합된 뒤에 다음 단계를 시작한다.
- 준비: 설계서 PR(docs/auth-design)이 아직 열려 있으면 아래 "PR 절차"대로 병합한다. main에 reference/auth-design.md가 있어야 시작한다
- 1단계: 기반. contracts/auth.md, dashkit_auth 스키마와 dash_auth 계정, make auth-init, make admin, 로그인·로그아웃·세션,
  요청 보호, 로그인 화면, 웹앱 셸의 401 처리 (3절의 첫 admin, 5-2, 7-2, 7-4, 7-5, 10절, 11-1 일부)
- 2단계: 접근 제어. 그룹 표, 탭 판정, /api/app·/api/guest-token·/api/data 필터, 그룹 API와 편집 화면 (4절, 11-3의 그룹·탭)
- 3단계: 가입과 메일. 가입, 메일 인증, 비밀번호 찾기·재설정, 테스트 모드와 테스트 메일함, 기본 그룹, 잠금, 비밀번호 정책
  (5-1, 5-3, 6절, 7-1, 7-3, 4-3의 기본 그룹)
- 4단계: 운용 화면. 사용자 목록·상세, 임의 가입·초대·일괄 초대, 리셋 두 방식, 정지, 삭제, 일괄 그룹 지정, 내 정보
  (5-4 ~ 5-8, 8-2, 11-2, 11-3의 사용자)
- 5단계: 통계와 기록. 접속 통계, 감사 로그, 보존 기간 정리 (9절)
설계서 2-3 "하지 않는 것"(SSO, 2단계 인증, Studio 인증, Superset 계정 연동, 행 단위 권한)과
AUTH_MAIL_MODE=smtp의 실제 발송 구현은 하지 않는다. smtp는 Mailer 인터페이스와 "구현되지 않음" 오류까지만 둔다.

# 단계마다 하는 일
1. main을 최신으로 받고 브랜치를 만든다. 이름은 기존 방식대로 feat/auth-….
2. 계약을 먼저 고친다. contracts/auth.md(1단계에서 새로 쓰고 이후 단계에서 채운다)와 contracts/api.md, contracts/README.md 색인을
   그 단계의 구현과 같은 PR에서 맞춘다. 구현이 계약과 어긋나면 안 된다.
3. 설계서의 해당 절을 구현한다. 서로 독립적인 작업(예: API와 화면, 사용자 API와 그룹 API)은 서브에이전트에 병렬로 맡기고,
   너는 계약, DB 스키마, 통합을 맡는다. 서브에이전트 둘이 같은 파일을 고치게 하지 않는다.
4. 13절 표의 그 단계 완료 조건을 테스트로 확인한다. make test-unit과 make test가 모두 통과해야 한다.
5. "PR 절차"를 따른다.

# 구현 규칙
- 호스트에는 Docker와 make만 있다고 가정한다. 파이썬 작업은 tools 컨테이너에서 실행한다.
- 새 의존성은 argon2-cffi 하나만 추가하고 버전을 정확히 고정한다.
- DB 계정 경계를 지킨다: 대시보드 데이터 읽기는 dash_reader만, 인증·운용 API는 dash_auth만, backend에는 owner 계정과 Superset 계정을 주지 않는다.
  dash_auth는 raw·dash를 읽지 못하고 dash_reader는 dashkit_auth를 읽지 못한다는 것을 테스트로 고정한다.
- 권한 검사는 서버에서 한다. 화면에서 버튼을 숨기는 것만으로 끝내지 않는다. 3절의 규칙(operator는 user만, 마지막 admin 보호, 자기 자신 보호)마다 테스트를 둔다.
- 테스트 메일함(GET /api/admin/outbox)은 operator에게 받는 계정의 등급이 user인 메일만 돌려준다(6절). operator가 admin·operator 주소로
  비밀번호 찾기를 요청해도 그 링크를 볼 수 없다는 것을 테스트로 고정한다.
- 비밀번호, 임시 비밀번호, 토큰, 해시를 로그·감사 로그·오류 응답·테스트 출력에 싣지 않는다. 비밀값은 코드와 커밋에 넣지 않고 환경변수로만 받는다.
- 가입·비밀번호 찾기·로그인 실패 응답으로 계정 존재 여부를 구분할 수 없어야 한다(5-1, 5-2, 5-3). 테스트로 고정한다.
- 사용자 입력이 들어가는 SQL은 전부 매개변수 바인딩이다. 식별자는 psycopg.sql.Identifier로만 넣는다.
- AUTH_EMAIL_DOMAINS의 개발용 값은 <사내 도메인>이다. .env.example에는 example.com을 넣는다.
- 기존 예시 프로젝트(devtracker, sales-sample, chart-gallery)의 설정 파일은 고치지 않는다. dashboard.yaml 형식에 권한 정보를 넣지 않는다(권한은 DB에 있다).
- 템플릿 코드(dashkit/, web/, superset/)에 예시 도메인 단어를 넣지 않는다. tests/test_domain_words.py가 계속 통과해야 한다.
- 화면은 기존 웹앱 방식을 따른다: 바닐라 JS, 빌드 단계 없음, 문구는 web/strings.js, 인라인 스크립트 없음(CSP), 기존 디자인 토큰.
- 기존 테스트가 로그인 없이 /api/app 등을 부른다. 테스트에 로그인 도우미(tests/conftest.py)를 넣어 고치고, 기대값을 느슨하게 바꾸거나 테스트를 건너뛰거나 지우지 않는다.
  e2e 화면 캡처(e2e/, .github/workflows/ui-screenshots.yml)도 로그인한 상태로 찍게 고친다.
- Studio의 미리보기 iframe(웹앱)은 로그인 화면을 보여 줘도 된다. Studio 자체에는 인증을 넣지 않는다.
- 타입 힌트를 유지한다.
- 개발 스택(웹앱 8080, Superset 8088)은 내가 쓰던 상태(PROJECT=devtracker)로 남겨 둔다. 테스트로 바꿨다면 되돌린다.
  1단계를 병합한 뒤에는 개발 스택에 make auth-init을 실행해 두고, admin 계정은 만들지 않는다(내가 make admin으로 직접 만든다).
- UI를 바꾼 단계는 헤드리스 브라우저로 화면을 직접 확인한다. 라이트·다크, 1280px·390px.

# PR 절차
1. 커밋하고 푸시한 뒤 gh pr create로 PR을 올린다. .github/pull_request_template.md 형식을 채운다.
   - UI 변경이 없으면 "UI 변경 없음"이라고 쓴다. 있으면 변경 전·후 화면 캡처를 넣는다.
   - 본문에 설계서의 어느 절을 구현했는지, 완료 조건의 확인 결과(테스트 출력 요약), 스스로 정한 판단을 쓴다.
2. 리뷰를 기다린다. 리뷰어는 Codex(chatgpt-codex-connector[bot])이고 보통 PR을 올리고 몇 분 안에 요약 댓글과 줄 단위 댓글을 단다.
   - gh pr view, gh api repos/ohyounjo/dashboard/pulls/<번호>/comments 로 확인한다. 2분 간격으로 최대 20분 기다린다.
   - GitHub Actions 검사(tests, ui-screenshots)가 돌면 끝날 때까지 기다린다.
3. 리뷰 댓글을 처리한다.
   - P0, P1: 반드시 고친다. 인증·권한·비밀값에 관한 지적은 등급과 상관없이 P1로 다룬다.
   - P2: 타당하면 고친다. 고치지 않으면 이유를 그 댓글에 답글로 남긴다.
   - 지적이 틀렸다고 판단하면 근거(코드 위치, 테스트 결과)를 답글로 남기고 고치지 않는다.
   - 고친 것은 테스트를 다시 돌린 뒤 새 커밋으로 푸시하고(강제 푸시 금지), 각 댓글에 반영한 커밋 해시와 내용을 한국어로 답글로 남긴다.
4. 푸시한 뒤 다시 2번으로 돌아가 재리뷰를 기다린다(최대 10분). 이 반복은 PR당 최대 3번이다.
5. 아래를 모두 만족하면 gh pr merge --merge로 병합하고 브랜치를 지운다.
   - 처리되지 않은 P0, P1 지적이 없다
   - make test-unit과 make test가 마지막 커밋에서 통과했다
   - GitHub Actions 검사에 실패가 없다
   - 20분 안에 리뷰가 달리지 않았다면: 위 두 조건을 만족할 때 병합하고, PR에 "리뷰 없이 병합함"이라고 댓글을 남긴다
6. 병합 뒤 main을 받아 make up && make apply가 되는지, 로그인 없이 /api/app이 401인지 확인하고 다음 단계로 간다.

# 멈추는 조건
아래 경우에는 그 단계에서 멈추고, 뒤 단계를 시작하지 않는다. PR은 열어 둔 채(또는 draft로) 상황을 댓글로 남긴다.
- 리뷰 반복 3번 뒤에도 P0 또는 P1이 남았다
- 테스트를 통과시킬 수 없다
- 완료 조건을 만족하려면 설계서의 기능 범위(2절), 권한 규칙(3절), DB 계정 경계(7-5)를 어겨야 한다
- backend에 owner 계정이나 Superset 계정을 줘야만 한다
- 기존 예시 프로젝트 설정을 고쳐야만 한다
- 데이터를 지우는 작업(make reset, 볼륨 삭제, 강제 푸시, main 직접 푸시)이 필요하다. 이런 작업은 하지 않는다.
  기존 data-db 볼륨에 dash_auth 계정과 dashkit_auth 스키마를 더하는 것은 make auth-init으로 하고 볼륨을 다시 만들지 않는다

# 금지
- main에 직접 커밋하거나 푸시하지 않는다. 강제 푸시하지 않는다.
- 이 저장소(ohyounjo/dashboard) 밖의 외부 서비스에 올리거나 배포하지 않는다. 실제 메일을 보내지 않는다.
- .env와 비밀값을 PR, 댓글, 로그에 쓰지 않는다.
- 내 개발 스택의 볼륨과 .state/를 지우지 않는다.
- 포트를 127.0.0.1 밖으로 열지 않는다. 사내 공개(12절 마지막 항목)는 이 작업의 범위가 아니다.
````
