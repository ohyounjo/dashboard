## 1. 요약

지금은 테이블마다 CSV 파일 하나가 데이터의 전부다. 행을 더하려면 전체 파일을 다시 만들어 `make apply`를 돌려야 하고, 로그인한 운용자가 데이터를 올리거나 들여다볼 길이 없다. 이 설계는 다음을 넣는다.

- **추가 적재:** 테이블은 첫 CSV로 만들어지고, 그 뒤의 데이터는 이미 있는 테이블에 **더해진다**. 한 번에 더한 묶음이 배치 하나다(5절).
- **하나씩도, 대량으로도:** 폼에 한 행을 입력하는 것, 표를 붙여넣는 것, 큰 CSV를 올리는 것, 여러 테이블의 파일을 한꺼번에 올리는 것이 모두 같은 길을 탄다. 미리보기·이력·취소가 똑같이 붙는다(5-2, 9-2).
- **원본은 계속 파일이다.** 더한 배치를 프로젝트 폴더의 파일로 남기고, DB는 지금처럼 그 파일들에서 만든 결과물이다. 그래서 `make apply`로 언제든 같은 DB를 다시 만들 수 있다(4절).
- **테이블·열을 운영 중에 추가:** 새 CSV를 올려 테이블을 만들고, 있는 테이블에 열을 더한다. **열 추가는 가능하다**(6절).
- **그래프와 테이블의 관계:** 그래프는 데이터셋 하나를, 데이터셋은 테이블 하나 이상을 본다. 이 구조로 그래프 1 : 테이블 N, 그래프 N : 테이블 1이 모두 성립한다. 무엇이 무엇을 쓰는지는 계보로 기록해 보여 준다(7절).
- **조회:** 운용자가 테이블 행을 걸러 본다. 모든 조회는 서버가 한 번에 200행까지로 끊는다(8절).
- **운용 화면:** 기존 `web/admin/`에 데이터 메뉴를 더한다(9절).
- 이 일을 맡는 **관리 서비스(manager)** 를 backend와 따로 둔다. backend는 지금처럼 읽기 전용이다(10절).

용어: **테이블**은 `schema.yaml`의 테이블(`raw.<이름>`), **데이터셋**은 `dashboard.yaml`의 `datasets`(`dash.<이름>` 뷰), **그래프**는 Superset 차트와 웹앱 위젯 섹션, **배치**는 한 번에 더한 행의 묶음(파일 하나)이다. **운용자**는 `admin`과 `operator`다(`contracts/auth.md`).

### 2-3. 하지 않는 것

- **Superset이 이미 하는 일을 다시 만들지 않는다**(보강설계서 9절과 같은 원칙).
  - 저장 쿼리, 쿼리 공유. SQL 콘솔은 실행 한 번이 전부다.
  - 조인·합치기를 위한 설정 문법(`join`, `union` 같은 것). 여러 테이블을 묶는 일은 지금처럼 `sql:` 데이터셋이 한다(7-1).
  - 차트 편집. 그래프를 더하고 고치는 일은 설정 파일과 Studio가 한다. 운용 화면은 데이터와 데이터셋까지만 다룬다.
- **행 삭제와 임의 수정.** 화면에서 하는 일은 행을 **더하는 것**이다. `update` 정책의 테이블은 같은 키로 다시 넣으면 고쳐지므로 "이 행 고치기"가 된다(5-2). 행을 빼는 길은 배치 되돌리기뿐이다.
- 쓰기 SQL(INSERT·UPDATE·DDL), Superset SQL Lab을 운용자에게 여는 것.
- 여러 프로젝트의 동시 운영(보강설계서 5-6). 프로젝트 전환은 지금처럼 동작한다(4-4).
- 실시간(행 단위 스트림) 적재, 행 단위 권한, `user` 등급의 데이터 조회·올리기.

## 3. 원칙과의 대조

### 3-1. 지금 구조에서 걸리는 점

| 지금 | 이 요청에서 걸리는 점 |
|---|---|
| 테이블 하나 = `data/<테이블>.csv` 하나. `load`가 매번 전체를 다시 넣는다 | 데이터를 **더할** 자리가 없다 |
| CSV 머리글은 스키마의 열과 **정확히 같은 집합**, UTF-8, 날짜는 `YYYY-MM-DD`만 | 열을 더한 뒤 옛 형식의 파일을 받을 수 없고, 엑셀에서 저장한 파일이 자주 걸린다 |
| backend는 `dash_reader`·`dash_auth`만 갖고 `projects/`는 읽기 전용이다 | 로그인한 사람이 쓸 수 있는 경로가 없다 |
| 쓰기 권한이 있는 Studio는 인증이 없고 `127.0.0.1` 전용이다 | 운용자가 쓸 수 없다 |
| `dash_reader`는 `raw`를 읽지 못한다(권한 경계, `tests/test_loader.py`) | 운용자가 테이블 원본을 볼 읽기 계정이 없다 |
| 검증이 파일 전체를 메모리에 올린다(`dashkit/loader/validate.py`) | 큰 파일을 받을 수 없다 |
| 프로젝트 잠금이 프로세스 안의 잠금이다(`dashkit/studio/store.py`의 `threading.Lock`) | 쓰는 프로세스가 둘 이상(Studio, manager, CLI)이 되면 서로를 막지 못한다 |

### 3-2. 원 설계의 원칙과 이 설계

| 원칙(`reference/plan.md`) | 이 설계 |
|---|---|
| 범용: `projects/<이름>/` 폴더만 바꾸면 다른 대시보드. 템플릿 코드에 도메인 단어 없음 | 지킨다. 더하는 설정 키는 도메인과 무관하고, 지정하지 않으면 지금과 똑같이 동작한다(설정 버전 1 그대로). 입력 폼도 `schema.yaml`에서 만들어지므로 테이블마다 화면 코드를 쓰지 않는다 |
| 재현성: 새 머신에서 `make up && make apply`면 같은 화면 | **지킨다.** 더한 배치를 프로젝트 폴더의 파일로 남기므로 DB는 언제든 다시 만들 수 있다(4절) |
| 로더는 매번 `raw`·`dash`를 통째로 다시 만든다 | 지킨다. 누적 테이블도 같은 경로로 다시 만든다. 운영 중의 추가 적재만 그 배치를 DB에 바로 더하고, 그 결과가 다시 만든 것과 같다는 것을 테스트로 고정한다(5-7) |
| 무엇을 바꾸든 `make apply` 하나 | 지킨다. 운용 화면의 구조 변경도 "설정 파일을 고치고 apply"다. 새 명령은 `make ingest` 하나다 |
| 차트는 Superset이 그린다. Superset 기능을 다시 만들지 않는다 | 지킨다(2-3) |
| backend는 owner DB 계정과 Superset 계정을 갖지 않는다 | 지킨다. 쓰기는 별도 서비스가 한다(10-1) |
| 설정 형식의 기준은 `contracts/` 하나, 해석은 `dashkit` 패키지 하나 | 지킨다. Studio와 manager가 같은 코어를 쓴다(10-2) |
| 추가할 때 고칠 곳은 파일 하나(보강설계서의 레지스트리·매니페스트) | 접수 방식, 값 다듬기, 충돌 정책, 입력 부품, 운용 메뉴를 같은 방식으로 만든다(5-8, 9-4) |

바뀌는 것은 둘이다(13절 D2, D3에서 확정).

| 지금 | 바뀌는 내용 |
|---|---|
| 운영 환경에 쓰기 도구를 두지 않는다(보강설계서 9절). 데이터 변경 경로는 CSV와 `make apply`뿐 | 로그인한 운용자만 쓰는 **관리 서비스**를 둔다. 하는 일은 여전히 "프로젝트 폴더의 파일을 고치고 반영"이다. 대시보드 화면은 계속 보기 전용이다 |
| 읽기 경로에서는 reader 계정만 쓴다(`AGENTS.md`) | 읽기 전용 계정이 둘이 된다: 대시보드용 `dash_reader`, 운용자 조회용 `dash_inspect` |

| 판 | 바꾼 것 | 이유 |
|---|---|---|

| 2판 | 저장 쿼리, 쿼리를 데이터셋으로 올리기, `join`·`union` 축약을 뺌 | Superset SQL Lab과 `sql:` 데이터셋이 하는 일이다 |

| 3판 | **받을 때는 너그럽게, 저장은 정규형으로.** 접수 단계가 인코딩·구분자·머리글·값 표기를 맞추고, 배치 폴더에는 정규형 CSV만 둔다 | 사용자는 가진 파일을 그대로 올리고, 로더는 지금의 엄격한 한 형식만 읽는다. 2판의 "원본 인터페이스"가 로더까지 닿던 것을 접수 단계로 줄였다 |

## 4. 데이터 모델

### 4-1. 테이블 방식: `replace`와 `append`

`schema.yaml`의 테이블에 선택 키 둘을 더한다.

```yaml
tables:
  members:                    # mode 생략 = replace. 지금과 같다
    primary_key: id
    columns: { … }
  issues:
    mode: append              # replace(기본) | append
    on_conflict: update       # append 전용. error(기본) | skip | update  (5-5)
    primary_key: id
    columns: { … }
```

| | `replace`(기본) | `append` |
|---|---|---|
| 원본 파일 | `data/<테이블>.csv` 하나 | `data/<테이블>.csv`(있으면 첫 배치) + `data/<테이블>/` 폴더의 배치 파일들 |
| 테이블 내용 | 그 파일 | 배치를 **번호순으로 차례로** 넣은 결과. 같은 키가 다시 나오면 `on_conflict`대로 |
| 행을 더하려면 | 파일을 통째로 바꾼다(Studio, 손 편집) | 배치를 더한다(5절) |
| 알맞은 데이터 | 구성원·코드표 같은 작은 기준 정보, 예시 | 계속 쌓이는 기록(이슈, 거래, 주별 스냅샷) |

- `replace` 테이블에 `mode: append`만 더하면 기존 CSV가 첫 배치가 된다. 파일을 옮길 필요가 없다.
- 운용 화면에서 만드는 새 테이블(6-1)의 기본은 `append`다.

### 4-2. 배치 폴더와 정규형

```
projects/<프로젝트>/data/
├─ members.csv                          # replace 테이블(지금과 같다)
├─ _pending/                            # 끝나지 않은 폴더 작업의 기록(5-4). 평소에는 비어 있다
├─ issues.csv                           # append 테이블의 첫 배치(선택)
└─ issues/                              # append 테이블의 배치 폴더
   ├─ 000001-20261120T0910Z.csv.gz
   ├─ 000002-20261121T0102Z.csv.gz
   ├─ _removed/                         # 되돌린 배치. 로더가 읽지 않는다
   └─ _merged/                          # 합치기 전의 배치. 로더가 읽지 않는다
```

- **배치 파일의 이름은 `<번호>[-<덧붙임>].csv` 또는 `….csv.gz` 꼴이어야 한다.** 로더는 폴더 바로 아래의 배치를 **번호순**(숫자로 비교한다)으로 읽고, `data/<테이블>.csv`가 있으면 언제나 맨 앞에 읽는다. `_`나 `.`으로 시작하는 이름은 읽지 않는다. 그 밖의 이름이 있거나 같은 번호가 둘이면 `dashkit check`와 load가 오류로 알리고 그 테이블을 읽지 않는다. 이름순에 기대면 안 되는 이유: `z.csv` 같은 파일이 있으면 나중에 더한 `000001-….csv.gz`가 다시 만들 때 그보다 먼저 읽혀, 바로 더한 결과와 다시 만든 결과가 달라진다(5-7).
- **배치 파일은 정규형이다:** UTF-8, 쉼표 구분, 머리글은 스키마의 열 이름, 값은 지금 검증기가 받는 표기(`YYYY-MM-DD`, `true`/`false` 등). **머리글에는 그 배치가 실제로 받은 열만 있다**(스키마 열의 부분집합, 스키마 순서). 빠진 열을 채워 넣지 않는다. 그래야 "보내지 않은 열"과 "일부러 비운 열"의 차이가 파일에 남아, 다시 만들 때도 바로 더했을 때와 같은 결과가 된다(5-5). 로더는 값의 표기에 지금의 엄격한 검증을 그대로 쓰고, 머리글만 누적 테이블의 배치에 한해 부분집합을 받는다(기본 키 열은 반드시 있어야 한다). 사용자가 올린 여러 모양의 입력을 정규형으로 바꾸는 일은 접수 단계(5-3)가 한다.
- manager는 `<6자리 번호>-<UTC 시각>.csv.gz`로 쓴다. 번호는 지금까지 쓴 가장 큰 번호 + 1(`_removed/`·`_merged/` 포함), 시각은 더한 때다. 그래서 새 배치는 언제나 지금 있는 모든 배치의 뒤에 온다. 올린 파일의 이름은 경로로 쓰지 않는다.
- 손으로 정규형 파일을 폴더에 넣어도 같다. 이름 규칙만 지키면 된다(지금 가장 큰 번호보다 큰 번호를 붙인다). manager가 쓴 것과 손으로 넣은 것이 같은 파일이라는 지금의 원칙 그대로다.
- **테이블 내용은 (`schema.yaml`, 번호순 배치 파일들)만으로 정해진다.** 따로 목록 파일을 두지 않는다. 언제 더했는지는 파일 이름에, 누가 더했는지는 감사 로그에 있다(10-4). 감사 로그가 없어져도 데이터는 같다.
- 운영 프로젝트의 배치 폴더는 저장소에 넣지 않고 폴더째 백업한다(13절 D5). 예시와 테스트 픽스처는 지금처럼 저장소에 둔다.

### 4-3. 열 규칙 추가: `default`, `aliases`

| 키 | 뜻 |
|---|---|
| `default: <값>` | **새로 들어가는 행**에서 배치에 그 열이 없을 때 쓰는 값(없으면 NULL). 이미 있는 행을 고칠 때는 쓰지 않는다(5-5). 열을 더하기 전의 옛 배치로 들어간 행이 이 값으로 채워지고(6-2), 입력 폼에 미리 채워진다 |
| `aliases: [<머리글>, …]` | 올린 파일의 머리글이 이 이름이면 이 열로 본다(5-3). 예: `aliases: ["Ship Status", "배송 상태"]` |

### 4-4. DB는 그대로 결과물이다

- 스키마는 지금과 같은 셋이다: `raw`, `dash`, `dashkit_meta`. 새 스키마를 만들지 않는다.
- `load`는 지금처럼 한 트랜잭션에서 셋을 통째로 다시 만든다. 누적 테이블은 배치를 차례로 넣는다. 그래서 **프로젝트 전환, `make reset`, 새 머신으로 옮기기가 지금과 똑같이 동작**하고, 백업은 프로젝트 폴더를 복사하는 것이다.
- 적재 기록에 더하는 것(`contracts/plan.md` "적재 기록"):

  ```sql
  CREATE TABLE dashkit_meta.batch (
    table_name text NOT NULL,
    file       text NOT NULL,            -- 원본 파일 이름. 누적 테이블은 배치마다, replace 테이블은 그 CSV 하나
    sha256     text NOT NULL,            -- 정규형 파일의 해시
    added_at   timestamptz,              -- 파일 이름의 시각. 이름에 없으면 NULL
    rows       integer NOT NULL,
    inserted   integer NOT NULL, updated integer NOT NULL, skipped integer NOT NULL, unchanged integer NOT NULL,
    PRIMARY KEY (table_name, file)
  );
  ```

  **프로젝트의 모든 원본 데이터 파일**이 한 줄씩 들어간다(`replace` 테이블의 CSV도 넣는다. 10-3의 대조가 쓴다). 원본 값은 없다(이름, 해시, 행 수뿐). `dash_reader`가 읽을 수 있다. 스냅샷에는 `tables.<이름>.mode`, `datasets.<키>.sources`(7-2), 그리고 **데이터 설정 지문** `data_revision`을 더한다. 데이터 설정 지문은 DB의 내용을 정하는 설정만으로 구한 해시다: `schema.yaml`의 `tables` 전체(열, 규칙, 방식, 충돌 정책, `checks`)와 `dashboard.yaml`의 `datasets`·`app.as_of`. 탭이나 그래프 배치처럼 DB와 상관없는 설정은 넣지 않는다(그런 것은 apply 없이 고쳐 쓰는 것이 지금의 동작이다). 누적 테이블의 행 지문은 남기지 않는다.
- `dashkit plan`은 누적 테이블을 배치 단위로 비교한다: 기록에 없는 파일은 "배치 +1", 기록에 있는데 폴더에 없는 파일은 "배치 −1". 이름과 해시가 같은 배치는 다시 읽지 않는다.

### 4-5. DB 계정

| 계정 | 권한 | 쓰는 곳 |
|---|---|---|
| `dash_owner` | `raw`·`dash`·`dashkit_meta` 소유(그대로) | 로더(tools·studio), manager의 **적재·다시 만들기** |
| `dash_reader` | `dash`·`dashkit_meta` SELECT(그대로) | backend, Superset, plan |
| `dash_auth` | `dashkit_auth` 표(그대로) | backend, manager의 로그인 확인·감사 로그 |
| `dash_inspect`(신규) | `raw`·`dash`·`dashkit_meta`의 **SELECT만**. 민감 열과 그것을 읽는 뷰는 뺀다(10-4) | manager의 행 조회·SQL 콘솔·내보내기 |

- `dash_inspect`는 쓰기 권한이 없고 `dashkit_auth`를 읽지 못한다. `dash_reader`는 계속 `raw`를 읽지 못한다. 테스트로 고정한다.
- 역할은 `data-db/init/`과 `make data-init`이 만들고, `raw`에 대한 권한은 로더가 적재 때마다 준다(`dash_reader`에게 `dash` 권한을 주는 것과 같은 방식).
- manager의 읽기 경로(조회·콘솔·내보내기·목록)는 `dash_inspect`만 쓴다. owner 연결은 쓰기 작업에서만 연다.

## 5. 추가 적재

### 5-1. 한 길

입력 방법이 무엇이든 같은 네 단계를 지난다.

```
직접 입력(한 행) ─┐
붙여넣기(여러 행) ─┼─▶ ① 접수 ─▶ ② 검증 ─▶ ③ 반영 ─▶ ④ 확정
파일 ─────────────┤    모양을      schema.yaml   DB에 더하고   정규형 파일을
여러 파일 ─────────┤    정규형으로   규칙          정책·checks   배치 폴더에
CLI · API 토큰 ───┘
```

- **한 행도 배치다.** 폼으로 넣은 한 행은 한 줄짜리 배치 파일이 된다. 그래서 검증 규칙, 미리보기, 이력, 취소, 감사 로그가 방법과 상관없이 같다.
- 구현도 한 벌이다: `dashkit/ingest`의 `ingest(project, items)` 하나를 REST·CLI·Studio가 부른다. `items`는 (테이블, 입력) 쌍의 목록이고 파일 하나는 그 한 개짜리 경우다.
- 같은 행들을 폼, 붙여넣기, 파일로 넣었을 때 **배치 파일이 바이트 단위로 같아야 한다.** 테스트로 고정한다.

### 5-2. 입력 방법 (R1, R7)

| 방법 | 알맞은 때 | 요청 | 응답 |
|---|---|---|---|
| **직접 입력** | 한두 행을 지금 넣는다 | `POST /tables/{t}/batches`, JSON `{"rows": [{…}]}` | 바로(200) |
| **붙여넣기·여러 행 입력** | 엑셀에서 수십~수백 행을 복사해 온다 | 위와 같다. 한 번에 500행(`INGEST_INLINE_MAX_ROWS`)까지, 넘으면 413 `too_many_rows`(파일로 안내) | 바로(200) |
| **파일** | 수천~수백만 행 | `POST /tables/{t}/batches`, multipart `file` | 작업(202) |
| **여러 파일** | 여러 테이블을 한꺼번에, 서로 참조하는 데이터 | `POST /batches`, multipart `files` 여러 개 + `map`(파일 이름 → 테이블) | 작업(202) |
| CLI | 서버에서 스크립트로 | `make ingest TABLE= FILE=` | 같은 함수 |
| API 토큰(선택) | 다른 시스템이 주기적으로 | 위의 REST 그대로, 인증만 다르다(10-5) | |
| 폴더에 직접 넣기 | 정규형 파일을 이미 갖고 있다 | 배치 폴더에 두고 `make apply` | 이미 된다(4-2) |

- **이 행 고치기:** `update` 정책의 테이블은 행 조회에서 행을 골라 기존 값이 채워진 폼을 열 수 있다. 다른 정책의 테이블에는 이 버튼이 없다.
  - 폼을 열 때 그 행을 **기본 키로 따로 읽는다**(8-1의 한 행 읽기). 목록의 값은 2,000자에서 잘려 있을 수 있으므로 폼에 쓰지 않는다.
  - 저장은 **기본 키와 바뀐 열만** 담은 한 행 배치다. 손대지 않은 열은 보내지 않으므로 그대로 남는다(5-5).
  - 값을 다 받지 못한 칸은 고칠 수 없게 잠근다: 한 행 읽기에서도 응답 한도 때문에 잘린 칸, 그리고 민감 열(값을 읽을 수 없다). 민감 열은 새 값을 넣는 것만 되고, 넣었을 때만 보낸다.
- **여러 파일은 한 트랜잭션이다.** 참조 순서(`config.table_order`)대로 넣고, 하나라도 실패하면 어느 파일도 들어가지 않는다. 부모와 자식 데이터를 함께 올릴 때 반쪽만 들어가는 일이 없다. 확정 도중에 프로세스가 죽어도 요청 단위로 복구한다(5-4). `map`을 생략하면 파일 이름(확장자 제외)이 테이블 이름과 같아야 한다. 한 번에 50개까지, 합계 `INGEST_MAX_REQUEST_MB`(기본 500).
- 큰 파일 하나의 한도는 `INGEST_MAX_UPLOAD_MB`(기본 200)·`INGEST_MAX_ROWS`(기본 2,000,000)다. 넘으면 나눠 올린다(여러 파일로 한꺼번에 올려도 된다).
- Superset의 CSV 업로드는 쓰지 않는다. `schema.yaml` 검증을 거치지 않고 관리 객체가 아니다.

### 5-3. 접수: 받을 때는 너그럽게, 저장은 정규형으로

사용자가 가진 입력을 그대로 받아 정규형(4-2)으로 바꾼다. 무엇을 어떻게 바꿨는지는 미리보기에 건수로 보여 준다(5-4). `strict=true`를 보내면 아무것도 바꾸지 않고 정규형만 받는다.

| 맞추는 것 | 규칙 |
|---|---|
| 인코딩 | UTF-8(BOM 허용)로 읽고, 안 되면 CP949로 읽는다(엑셀의 한글 CSV. `dashkit/scaffold.py`와 같은 방식) |
| 구분자 | 쉼표, 탭, 세미콜론 가운데 머리글 줄에서 판별한다. 붙여넣기는 탭이다 |
| 머리글 → 열 | 차례로 맞춘다: ① 열 이름 ② 그 열의 `aliases` ③ 그 테이블을 그대로 보는 데이터셋의 `labels`(화면 표시 이름) ④ 대소문자·공백·`_`·`-` 차이를 무시한 비교. 두 열에 맞으면 맞추지 않는다 |
| 맞지 않은 머리글 | 422 `unknown_columns`와 후보. 요청의 `columns`(`{"<머리글>": "<열>" 또는 null}`)로 사람이 정한다(`null`은 그 열을 버린다). admin은 그 맞춤을 `aliases`로 저장해 다음부터 자동으로 맞게 할 수 있다(`column.update` 연산) |
| 빠진 열 | 기본 키 열은 반드시 있어야 한다. 그 밖의 열은 없어도 받고, **채워 넣지 않고 없는 채로** 배치에 남긴다. 없는 열이 어떻게 되는지는 행마다 다르다(5-5): 새로 들어가는 행은 `default` 또는 NULL이 되고, 이미 있는 행은 그 열이 그대로다 |
| 값 | 유형별 다듬기(아래) |

값 다듬기는 유형마다의 등록 표다(`dashkit/ingest/normalize.py`의 `NORMALIZERS`).

| 유형 | 받아 주는 표기 → 정규형 |
|---|---|
| 모든 유형 | 앞뒤 공백 제거 |
| `date` | `2026/11/20`, `2026.11.20`, `20261120` → `2026-11-20`. **연도가 앞에 오는 형식만** 받는다(`11/20/2026`처럼 순서가 모호한 것은 오류로 둔다) |
| `integer`, `number` | 천 단위 쉼표 제거(`1,234,567` → `1234567`) |
| `boolean` | `Y`/`N`, `yes`/`no`, `1`/`0`(대소문자 무시) → `true`/`false` |
| `timestamp` | 날짜와 시각 사이의 공백·`T`, 위 날짜 표기 |

- JSON으로 온 행(직접 입력, 붙여넣기)도 같은 단계를 지난다. 값은 문자열로 바꿔 다룬다. 키가 있고 값이 `null`이거나 빈 문자열이면 "일부러 비움"(NULL)이고, 키가 아예 없으면 "보내지 않음"이다. 한 번에 보내는 행들은 **같은 열 집합**을 가져야 한다(다르면 422 `invalid_rows`). 배치 하나의 머리글은 하나이기 때문이다. 새 행을 넣는 폼은 모든 열을 보내고, 고치는 폼은 기본 키와 바뀐 열만 보낸다(5-2).
- 원래 올린 파일은 보관하지 않는다. 배치 폴더의 정규형 파일이 원본이 된다. 감사 로그에 원래 파일 이름과 해시를 남긴다.

### 5-4. 검증, 미리보기, 확정

1. **받기.** 파일은 디스크의 임시 파일로 받는다(메모리에 전부 올리지 않는다). 파일 이름 규칙은 Studio와 같다(`contracts/studio.md`).
2. **접수(5-3)** 뒤 **검증.** 규칙과 오류 형식은 지금의 CSV 검증과 같다(유형, `required`, `enum`, `min`·`max`, `pattern`, 묶음 안의 기본 키 중복). 한 줄씩 읽으며 검증한다. 오류 위치는 사용자가 올린 것 기준이다: 파일은 `<파일 이름>:<줄>:<열>`, JSON 행은 `rows[<번호>].<열>`. 참조(`ref`)는 DB에 있는 대상 테이블의 값과 대조하고(같이 올린 파일의 행 포함), 대상이 없는 값을 줄 단위로 보고한다.
3. **중복 확인.** 그 테이블에 같은 해시(정규형 기준)의 배치가 있으면 409 `duplicate_file`과 그 배치 이름. `force=true`면 진행한다. 인코딩만 다른 같은 파일도 걸린다. 해시는 미리 구해 두지만 **배치 기록과 견주는 일은 쓰기 잠금 안에서 한다**(10-3). 같은 파일을 동시에 두 번 보내도 뒤의 요청이 앞의 배치를 보고 거절된다.
4. **반영(트랜잭션 하나).** 임시 테이블에 COPY → 기존 행과 기본 키로 비교 → 충돌 정책(5-5) 적용 → `schema.yaml`의 `checks` 실행(위반 행이 있으면 롤백).
5. **확정.** 묶음 기록(`data/_pending/<묶음 id>.json`: 작업 종류 `add`와, 이 요청이 쓸 파일마다 테이블과 최종 이름)을 먼저 쓰고 → 정규형 파일들을 배치 폴더에 제 이름으로 옮기고 → 배치 기록(`dashkit_meta.batch`)을 더한 뒤 → 커밋하고 → 묶음 기록을 지운다. 커밋이 실패했거나 결과를 받지 못했으면 직접 치우지 않고, 아래의 복구 절차를 그대로 돌려 그 결과로 답한다(10-3). 파일 하나짜리 요청도 같은 절차다(묶음의 크기가 1이다).

결과 형식은 방법과 상관없이 같다.

```json
{ "ok": true,
  "batches": [ { "table": "issues", "file": "000007-20261121T0102Z.csv.gz",
                 "rows": { "total": 100000, "inserted": 99801, "updated": 150, "skipped": 0, "unchanged": 37, "invalid": 12 },
                 "normalized": { "encoding": "cp949", "delimiter": ",", "dates": 1204, "numbers": 0, "trimmed": 31 },
                 "columns": { "matched": { "배송 상태": "ship_status" }, "missing": ["memo"], "unknown": [] },
                 "errors": ["orders.csv:17:amount: 숫자가 아님 'abc'"], "error_count": 12,
                 "changes": [ { "key": "ISS-12", "before": { "status": "open" }, "after": { "status": "closed" } } ] } ] }
```

- **전부 들어가거나 하나도 들어가지 않는다.** 검증 오류, 충돌(`error` 정책), `checks` 위반, DB 오류 어느 것이든 테이블도 폴더도 그대로다. 여러 파일을 함께 올렸으면 그 전체가 한 단위다.
- **미리보기:** `dry_run=true`면 4번까지 하고 롤백한다. 결과 형식은 같다. `changes`는 `update` 정책에서 바뀔 행의 전후 값(앞 20개)이다.
- **다시 올리지 않고 확정:** 파일의 미리보기 결과에는 `upload_id`가 들어 있다. 받은 파일을 1시간 잡아 두고, `POST /tables/{t}/batches`에 `{"upload_id": "…"}`를 보내면 그 파일로 적재한다(여러 파일은 `POST /batches`에). 200MB를 두 번 올리지 않는다. 지났으면 410 `upload_expired`.
- **오류 행 빼고 넣기:** `skip_invalid=true`면 행 단위 검증 오류와 참조 오류가 난 행을 빼고 나머지를 넣는다. 배치 파일에는 **들어간 행만** 쓴다(다시 만들어도 같은 결과다). 빠진 행은 `GET /jobs/{id}/rejects`로 내려받는다(올린 행 + `오류` 열. 고쳐서 그 파일만 다시 올리면 된다). 민감 열의 값은 여기에도 싣지 않는다(10-4). 기본은 꺼져 있다. 키 충돌(`error` 정책)과 `checks` 위반은 빼고 넣는 대상이 아니다(전체 거절).
- **진행률:** 작업은 `progress`(`phase`, 읽은 바이트·전체 바이트, 읽은 행 수)를 갖는다. 화면을 떠나도 작업은 끝까지 간다.
- **반영 시점:** Superset의 데이터 캐시가 꺼져 있어(`superset_config.py`의 `NullCache`) 커밋하면 바로 그래프에 나온다. 행만 더하는 적재에는 sync가 필요 없다. 캐시를 켜는 배포는 5-8의 훅을 쓴다.
- **중간에 끊겼을 때: 요청 단위로 복구한다.** 확정 도중에 죽으면 묶음 기록이 남는다. 그 요청은 성공 응답을 받은 적이 없다. manager는 시작할 때와 다음 적재 전에, 로더는 `load`를 시작할 때 남은 묶음 기록을 먼저 처리한다(같은 함수 `ingest.recover`). 복구는 쓰기 잠금을 잡은 뒤에 한다. 살아 있는 작업은 모두 같은 잠금을 잡고 있으므로, 잠금을 잡은 쪽이 보는 기록은 전부 끊긴 작업의 것이다(10-3).

  | 남은 묶음 기록의 상태(**위에서부터 차례로 본다**) | 처리 |
  |---|---|
  | ① 적힌 배치가 배치 기록(`dashkit_meta.batch`)에 **있다**(커밋은 됐고 묶음 기록 지우기만 못 했다. 커밋 응답을 받지 못한 경우도 여기다) | 파일은 그대로 두고 묶음 기록만 지운다 |
  | ② 배치 기록에 없고, 적힌 파일이 **모두** 제자리에 있다 | 묶음 **전체**를 한 트랜잭션으로 반영하고 묶음 기록을 지운다(`load`는 어차피 전부 다시 넣으므로 기록만 지운다). 반영이 실패하면 ③처럼 전체를 치운다 |
  | ③ 배치 기록에 없고, 적힌 파일의 **일부만** 제자리에 있다 | 옮겨진 파일을 모두 지우고 묶음 기록을 지운다. 묶음 전체가 없던 일이 된다 |

  그래서 부모 파일만 옮겨진 채 죽어도 부모만 들어가는 일이 없다. **폴더를 바꾸는 다른 작업도 같은 기록을 먼저 쓴다**: 되돌리기·되살리기(종류 `remove`·`restore`, 5-6), 합치기(종류 `compact`, 6-4), 구조 변경(종류 `config`, 6-3). 복구 방법은 종류마다 그 절에 적는다. 읽기만 하는 `dashkit plan`은 남은 기록을 고치지 않고 "끝나지 않은 폴더 작업이 있음"을 알리며 그 테이블의 배치 비교를 하지 않는다. 묶음 기록 폴더 `_pending`은 테이블 이름이 될 수 없는 이름이라(`_`로 시작) 로더가 데이터로 읽지 않는다.
- **묶음 기록에 없는 파일**(손으로 폴더에 넣은 정규형 파일)이 배치 기록에 없으면, manager는 그 테이블의 다음 적재 전에 하나씩 차례로 반영한다. 그 파일의 번호가 이미 반영한 배치보다 앞이면 순서를 지킬 수 없으므로 409 `rebuild_required`로 apply를 요구한다. 이미 반영한 배치 파일이 바뀌었거나 없어진 경우도 같다(10-3의 대조 표).

### 5-5. 충돌 정책 (같은 기본 키가 이미 있을 때)

**테이블의 속성**이다(`on_conflict`). 더할 때마다 바꿀 수 없다. 배치를 다시 넣었을 때 같은 결과가 나오려면 정책이 배치마다 달라서는 안 된다.

| 정책 | 동작 | 알맞은 데이터 |
|---|---|---|
| `error`(기본) | 겹치는 키가 하나라도 있으면 전체를 거절한다(422 `key_conflict`, 앞 20개 키) | 다시 오면 안 되는 기록(거래, 로그) |
| `skip` | 먼저 들어온 행을 두고 새 키만 더한다 | 기간이 겹쳐 오는 주기 파일 |
| `update` | 같은 키의 행을 나중 배치의 값으로 바꾼다. **배치의 머리글에 있는 열만** 바꾼다: 머리글에 없는 열은 그대로 두고, 머리글에 있는데 칸이 비어 있으면 NULL로 바꾼다. 값이 모두 같은 행은 `unchanged`로 센다 | 상태가 바뀌는 데이터(이슈), 정정 |

어느 정책에서든 **새로 들어가는 행**의 머리글에 없는 열은 `default` 또는 NULL이다. `default`가 없는 `required` 열이 빠진 새 행은 오류이고(그 키를 알린다) 전체를 거절한다. 그래서 `{id: 1, status: "closed"}`만 보내면 이미 있는 1번 행은 `status`만 바뀌고 다른 열은 그대로다. 배치 파일의 머리글이 `id,status`로 남으므로 다시 만들어도 같다.

정책은 등록 표(`dashkit/ingest/policies.py`의 `POLICIES`)의 함수 하나씩이다.

### 5-6. 배치 이력과 되돌리기

- **이력:** 배치 기록(파일, 더한 시각, 행 수)에 감사 로그의 올린 사람·방법(`form`·`paste`·`upload`·`api`·`cli`)·원래 파일 이름을 붙여 보여 준다. 배치 파일을 내려받을 수 있다.
- **되돌리기 = 그 배치 파일을 빼고 다시 만들기.** 작업이 차례로 한다: 그 파일을 뺀 사본으로 검증(다른 테이블의 참조가 깨지는지) → 통과하면 파일을 `_removed/`로 옮기고 → `load`. 실패하면 파일을 건드리지 않는다. 폴더 안의 배치는 어느 것이든 뺄 수 있고, 결과는 "그 파일이 처음부터 없었을 때"와 같다. 첫 배치인 `data/<테이블>.csv`는 운용 화면에서 빼지 않는다.
- **방금 추가 취소(빠른 길):** 그 테이블의 **가장 최근 배치**이고 그 배치의 **모든 행이 새 키**였으면(기록의 `inserted`가 `rows`와 같다. `updated`·`skipped`·`unchanged`가 하나라도 있으면 아니다) 다시 만들지 않고 그 배치 파일에 있는 키의 행만 지운다. 같은 값으로 다시 보낸 행(`unchanged`)은 전부터 있던 행이라, 이 조건이 없으면 배치의 키를 지울 때 원래 행까지 지워진다. 같은 트랜잭션에서 프로젝트의 `checks`를 돌린다(10-3의 공통 순서). 위반하거나 다른 테이블의 행이 그 행을 참조하면 DB도 파일도 그대로 두고 422 `check_failed`로 이유를 알린다. 통과하면 파일을 `_removed/`로 옮기고 커밋한다. 바로 끝나므로 한 행을 잘못 넣고 취소하는 데 전체를 다시 만들지 않는다. 조건이 맞지 않거나 폴더의 배치 파일이 배치 기록과 다르면 위의 다시 만들기로 간다. 빠른 길의 결과가 다시 만든 것과 같다는 것을 테스트로 고정한다.
- `_removed/`의 파일은 운용 화면에서 되살리거나(같은 방식으로 다시 만든다) 지운다.
- **끊김 복구:** 되돌리기와 되살리기도 묶음 기록을 먼저 쓴다(5-4). 파일 옮기기는 이름 바꾸기 한 번이라 반쪽 상태가 없다. 옮긴 뒤 다시 만들기 전에 죽으면 기록이 남고, 복구는 다시 만들기(`load`)를 끝낸 뒤 기록을 지운다. 그때까지 DB에는 뺀 배치의 행이 남아 있으므로 운용 화면은 그 테이블에 "다시 만들어야 함"을 보인다.

### 5-7. 바로 더한 결과와 다시 만든 결과는 같아야 한다

운영 중의 추가 적재와 `load`의 다시 만들기는 **같은 함수**(`dashkit/ingest/apply.py`의 `apply_batch`)를 쓴다. `load`는 빈 테이블에 배치를 번호순으로 하나씩 이 함수로 넣는다. 그래서 경로가 하나이고, 테스트가 이것을 고정한다: 배치를 하나씩 더해 만든 테이블과 `make apply`로 처음부터 만든 테이블의 행이 같다(정책 셋 모두, 빠른 취소와 합치기 뒤에도).

### 5-8. 확장 지점

| 지점 | 등록 표 | 더하는 방법 |
|---|---|---|
| 접수 방식 | `PARSERS`(종류 → 파서). 파서는 `header() -> list[str]`과 `rows() -> Iterator[(위치, 값들)]`만 내놓는다. 1차는 `csv`(인코딩·구분자 판별)와 `rows`(JSON 행) | 클래스 하나와 표 한 줄. xlsx는 여기에 더한다. 원본 DB에서 가져오기는 그 결과를 접수에 넘기는 명령으로 만든다. **로더는 건드리지 않는다**(배치는 언제나 정규형이다). 보강설계서 5-5의 "행을 내놓는 함수" 그대로다 |
| 값 다듬기 | `NORMALIZERS`(유형 → 규칙 목록, 5-3) | 규칙 함수 하나 |
| 충돌 정책 | `POLICIES`(5-5) | 함수 하나와 스키마의 enum 값 하나 |

| 입력 부품 | `web/shared/fields.js`(열 유형 → 입력 부품, 9-4) | 표 한 줄 |

## 6. 테이블과 열을 운영 중에 바꾸기 (R5)

구조 변경은 **설정 파일을 고치고 apply**다. 운용 화면이 하는 일은 Studio와 같고(연산으로 YAML을 고친 뒤 check → load → sync), admin만 한다.

### 6-1. 테이블 추가

1. 운용 화면에 CSV를 놓는다 → `POST /api/manage/tables/infer`가 이름·유형·기본 키·참조를 추론해 돌려준다(`dashkit/scaffold.py`의 `infer_tables`, 형식은 `contracts/scaffold.md`. 이미 있는 테이블의 기본 키도 참조 후보로 본다). 파일은 아직 어디에도 쓰지 않는다.
2. 사람이 추론을 확인하고 고친다: 테이블 이름, 열 이름·유형, 기본 키, 방식(기본 `append`), 충돌 정책, **데이터셋도 만들지**(기본 켬), **초안 그래프와 탭도 만들지**(기본 끔, `suggest_dashboard`).
3. `POST /api/manage/tables` → 작업: `schema.yaml`에 테이블, `dashboard.yaml`에 `datasets.<이름>: { table: <이름> }`, 첫 파일을 정규형으로 넣은 사본을 검증(고른 방식에 따라 `append`는 `data/<이름>/`의 첫 배치 파일로, `replace`는 `data/<이름>.csv` 하나로 쓴다. `replace`의 파일은 모든 열을 머리글에 갖는다) → 통과하면 파일을 원자적으로 저장 → apply.

- 원래 머리글은 그 열의 `aliases`에 남긴다. 같은 모양의 파일을 다음에 올리면 머리글이 저절로 맞는다.
- 추가만 하므로 기존 테이블·그래프는 영향이 없다.
- apply가 load에서 실패하면 저장한 파일을 변경 전으로 되돌린다(6-3의 이력). sync에서 실패하면 지금 apply와 같이 다시 실행해 이어 간다.
- 새 탭을 만들었으면 `user` 등급에게는 그룹이 허용하기 전까지 보이지 않는다(`contracts/auth.md` "접근 제어").

### 6-2. 열 추가와 그 밖의 구조 변경

**열 추가는 가능하다.** 방식에 따라 하는 일이 조금 다르다.

- **`append` 테이블:** `schema.yaml`에 열을 더하고 apply하면 된다. 다시 만들 때 옛 배치에는 그 열이 없으므로 그 행들은 `default` 또는 NULL이 된다(누적 테이블의 배치는 머리글의 부분집합을 받는다, 4-2).
- **`replace` 테이블:** CSV 머리글이 스키마의 열과 정확히 같아야 한다는 지금의 규칙을 그대로 둔다. 그래서 `column.add` 연산이 `schema.yaml`과 함께 **그 테이블의 CSV에도 새 열을 더한다**(값은 `default`, 없으면 빈 칸). 두 파일을 한 번의 저장으로 바꾸고(6-3의 저장 방식), 검증에 실패하면 둘 다 그대로다. 손으로 고칠 때도 두 파일을 함께 고친다.

| 변경 | 지원 | 방법 | 주의 |
|---|---|---|---|
| 열 추가(선택 열) | 4단계 | `column.add` 연산 + apply. `replace` 테이블은 CSV에도 열을 더한다 | 기존 행은 `default` 또는 NULL |
| 열 추가(`required`) | 4단계 | 위와 같고 `default`가 반드시 있어야 한다 | 없으면 기존 행(옛 배치, `replace` 테이블의 CSV)이 검증에서 걸린다 |
| `enum` 값 추가, `min`·`max`·`pattern` 완화, 설명, `aliases` | 4단계 | `column.update` 연산 + apply | 규칙을 **좁히면** 옛 배치가 검증에서 걸린다. 오류가 파일·줄로 나온다 |
| 유형 넓히기(`integer` → `number`, 무엇이든 → `text`) | 4단계 | `column.update` 연산 + apply | 옛 배치를 새 유형으로 다시 읽는다. 그래프가 그 열을 쓰면 영향 목록을 먼저 보여 준다 |
| 열 이름 변경, 열 삭제, 유형 좁히기 | 후순위 | 합치기(6-4)를 변환과 함께 실행한다: 지금 내용을 새 구조의 파일 하나로 다시 쓴다 | 옛 배치 파일에는 옛 이름·옛 열이 남아 있어 그대로는 다시 읽을 수 없다 |
| 기본 키 변경 | 지원 안 함 | 새 테이블을 만들어 옮긴다 | |

열을 더한 뒤 무엇이 바뀌는가:

- `table:` 데이터셋에는 새 열이 자동으로 나온다(지금 `plan`도 "열 추가: …"로 보여 준다).
- `sql:` 데이터셋은 `t.*`로 쓴 곳에만 나온다. 열을 하나씩 적은 쿼리는 사람이 고쳐야 한다. 작업 결과에 "새 열이 나오지 않는 데이터셋"을 알린다(계보로 판정).
- 기존 그래프는 바뀌지 않는다. 새 열을 쓰려면 그래프를 더하거나 고친다.
- 입력 폼에는 새 열이 바로 나온다(폼은 `schema.yaml`에서 만든다). 새 열이 없는 옛 모양의 파일도 계속 올릴 수 있다.
- 파일을 올리다 스키마에 없는 머리글이 나오면(422 `unknown_columns`) 운용 화면이 고르게 한다: 있는 열에 맞추기, 버리기, 그리고 admin에게는 추론한 유형과 함께 "새 열로 추가하고 적재". 확인하면 열 추가 작업 뒤에 그 파일을 적재한다.

### 6-3. 설정 파일을 고치는 방식

- Studio의 방식 그대로다(`contracts/studio.md` "저장 방식"): 사본에 연산을 적용해 검증한 뒤 원자적으로 교체하고, 고친 곳만 다시 써서 주석과 모양을 남긴다. 연산을 더한다: `table.add`, `table.update`, `table.remove`, `column.add`, `column.update`, `dataset.add`, `dataset.update`, `dataset.remove`. Studio도 같은 연산을 쓴다.
- manager의 설정 변경 요청은 `revision`(읽을 때 받은 값)이 **필수**다. 그 사이에 다른 프로세스나 사람이 파일을 고쳤으면 409 `stale_config`다(10-3).
- backend는 파일 서명이 바뀌면 다음 요청부터 새 설정을 읽는다(`contracts/api.md` "설정 다시 읽기").
- **설정 변경 이력:** 설정을 고치는 작업은 **그 작업이 바꾸는 파일 전부**의 변경 전 사본을 `.state/history/<프로젝트>/<시각>-<동작>/`에 남긴다(최근 50개). 사본은 저장 전에 묶음 기록에 담고, load까지 끝난 변경만 이력에 옮긴다(되돌려진 변경은 남기지 않는다). 두 YAML과, `replace` 테이블의 열 추가처럼 함께 바뀌는 CSV(6-2)가 여기에 든다. 운용 화면에서 이전 판으로 되돌리면 그 파일들을 **함께** 되돌린다(되돌리기도 "파일을 바꾸고 apply"다). 그 뒤에 그 CSV가 다시 바뀌었으면 덮어쓰지 않고 거절한다(409 `stale_config`. 이력의 사본이 지금 내용의 바로 앞 판일 때만 되돌린다). 누적 테이블의 배치 파일은 이력에 넣지 않는다. 열을 더하기 전 설정으로 되돌려도 옛 배치는 그대로 읽힌다(새 열이 든 배치가 그 뒤에 들어왔다면 검증이 알린다). Studio는 지금처럼 git에 맡긴다.
- **끊김 복구:** 구조 변경은 파일을 여럿 바꿀 수 있고(두 YAML, `replace` 테이블의 CSV, 새 테이블의 첫 파일) 파일 하나하나의 교체만 원자적이다. 그래서 구조 변경 작업도 묶음 기록을 쓴다(종류 `config`, 10-3의 공통 순서). 순서는 이렇다: 쓰기 잠금 → 묶음 기록(바꿀 파일 목록, **변경 전 사본**, 새 설정의 데이터 설정 지문)을 쓴다 → 파일들을 바꾼다 → apply → 이력에 남기고 묶음 기록을 지운다. 도중에 죽으면 다음 복구가 정한다.

  | 남은 `config` 기록의 상태 | 처리 |
  |---|---|
  | DB의 `data_revision`이 기록의 새 지문과 같다(load까지 끝났다) | 새 파일을 그대로 두고 기록을 지운다. sync가 남았으면 apply를 다시 돌려 잇는다 |
  | 그 밖(파일을 일부만 바꿨거나, 다 바꿨지만 load 전이다) | 기록의 변경 전 사본으로 **모든 파일을 되돌리고** 기록을 지운다. 새로 만든 파일은 지운다 |

  복구는 manager가 시작할 때와 다음 작업 전에, 그리고 `dashkit check`·load가 설정을 읽기 전에 한다. 그래서 `schema.yaml`만 새 판이고 CSV는 옛 판인 채로 검증하는 일이 없다. backend는 그 사이 설정을 읽더라도 검증에 실패한 설정을 쓰지 않고 마지막으로 유효했던 설정으로 답한다(지금의 동작이다).
- 서버에서 고친 파일은 내려받아 사람이 저장소에 커밋한다(13절 D4).

### 6-4. 배치 합치기

한 행씩 더하면 한 줄짜리 배치 파일이 쌓인다. 내용에는 문제가 없지만 다시 만들 때 파일 수만큼 시간이 든다. 합치기가 이것을 정리한다.

- `POST /api/manage/tables/{t}/compact`(admin) → 작업. DB의 행은 바뀌지 않는다.
- **전제:** 시작할 때 그 테이블의 배치 파일과 배치 기록을 대조한다(10-3의 공통 순서). 반영되지 않았거나 바뀐 파일이 있으면 409 `rebuild_required`로 거절하고 apply를 요구한다. 합친 파일은 DB의 행에서 만들기 때문에, 반영되지 않은 배치가 있는 채로 합치면 그 행은 합친 파일에 없고 원본만 `_merged/`로 가서 잃는다.
- 순서는 이렇다.
  1. 지금 테이블의 행을 기본 키 순으로 정규형 **임시 파일**로 쓴다(`.`으로 시작하는 이름이라 로더가 읽지 않는다).
  2. 묶음 기록(종류 `compact`: 새 파일의 최종 이름·해시·행 수, 옮길 옛 파일 목록)을 쓴다.
  3. 그때까지의 배치 파일(과 `data/<테이블>.csv`)을 `_merged/<시각>/`으로 옮긴다.
  4. 임시 파일을 제 이름(`<다음 번호>-<시각>-merged.csv.gz`. 이름이 합친 배치의 표식이다)으로 바꾼다.
  5. 배치 기록을 고쳐 커밋하고 묶음 기록을 지운다.
- **끊김 복구:** 3~5 사이에 죽으면 묶음 기록이 남는다. manager와 로더는 **배치를 읽기 전에** 먼저 복구한다(5-4의 `ingest.recover`).

  | 남은 기록의 상태 | 처리 |
  |---|---|
  | 새 파일(임시 이름이든 제 이름이든)이 있고 해시가 기록과 같다 | **끝까지 진행한다**: 남은 옛 파일을 모두 옮기고, 새 파일을 제 이름으로 두고, 배치 기록을 고친다 |
  | 새 파일이 없거나 해시가 다르다 | **전체를 되돌린다**: `_merged/<시각>/`으로 옮긴 파일을 제자리로 돌리고 새 파일을 지운다 |

  그래서 로더가 옛 배치의 일부와 그 행을 이미 담은 합친 배치를 함께 읽는 일이 없다.
- 합친 뒤 다시 만든 결과가 합치기 전과 같다는 것을 테스트로 고정한다(5-7).
- 합친 배치는 하나씩 되돌릴 수 없다(409 `merged_batch`. 그 테이블의 행 전부를 담는다). `_merged/`는 합친 뒤의 apply가 한 번 성공한 것을 확인하고 지운다.
- 배치 수가 `INGEST_COMPACT_HINT`(기본 200)를 넘으면 운용 화면이 그 테이블에 "합치기 권장"을 보인다. 자동으로 하지는 않는다.
- 열 이름 변경·삭제(6-2)는 이 작업에 "새 구조로 바꿔 쓰기"를 더한 것이다.

## 7. 그래프와 테이블의 관계 (R3)

### 7-1. 모델

```
테이블 raw.<t>   N ── M   데이터셋 dash.<d>(뷰)   1 ── N   그래프(차트·위젯 섹션)   N ── 1   대시보드·탭
```

- **그래프는 데이터셋 하나를 본다.** Superset 차트 하나가 데이터 원본 하나를 갖는 제약이고, 위젯 섹션도 같다.
- **데이터셋은 테이블 하나 이상을 본다.** 한 테이블을 여러 데이터셋이 볼 수도 있다.

| 관계 | 어떻게 성립하나 | 예 |
|---|---|---|
| 그래프 N : 테이블 1 | 여러 그래프가 같은 데이터셋을 본다. 가공이 다르면 같은 테이블에 데이터셋을 여럿 둔다 | `devtracker`의 `kpi_snapshots`를 차트 셋이 쓴다 |
| 그래프 1 : 테이블 N | 그래프가 여러 테이블을 묶은 `sql:` 데이터셋을 본다 | `devtracker`의 `issues` = issues + milestones + members |

관계는 지금 구조로 성립한다. 새 문법을 만들지 않는다. 이 설계가 더하는 것은 둘이다.

- **운용 화면에서 데이터셋 만들기(admin):** 새 테이블을 기존 테이블과 묶으려면 `sql:` 데이터셋이 필요하다. 운용 화면에서 키와 SELECT 문을 넣으면 `dataset.add` 연산으로 `dashboard.yaml`에 더하고 apply한다. 쿼리가 틀리면 지금처럼 load의 뷰 생성 단계가 오류를 돌려주고 파일은 되돌린다.
- **관계를 기록하고 보여 주기(7-2).**

서로 다른 테이블의 지표를 한 그래프에 그릴 때(예: 월별 매출과 방문 수)는 공통 축으로 묶은 `sql:` 데이터셋을 만들어 `mixed` 같은 유형으로 그린다.

### 7-2. 계보

- **데이터셋 → 테이블·열:** 로더가 뷰를 만든 직후 PostgreSQL의 의존 정보(`information_schema.view_column_usage`, 뷰가 뷰를 쓰면 끝까지 따라간다)를 읽어 적재 스냅샷의 `datasets.<키>.sources`에 적는다. 쿼리 글에서 이름을 찾는 방식보다 정확하다.
- **그래프 → 데이터셋·열:** 설정에서 계산한다(`config.referenced_columns`).
- `GET /api/manage/lineage`가 테이블·데이터셋·그래프·대시보드·탭과 그 사이의 선을 돌려준다. 스냅샷은 `dash_reader`가 읽을 수 있어 owner가 필요 없다.

쓰이는 곳:

- 테이블 상세의 "쓰이는 곳"(이 테이블을 읽는 데이터셋 → 그래프 → 탭).
- 열 유형을 바꾸거나 테이블을 지우기 전에 영향받는 그래프 목록을 보여 준다. 쓰는 곳이 있는 테이블은 삭제를 거절한다(409 `in_use`).
- 열을 더한 뒤 새 열이 나오지 않는 `sql:` 데이터셋을 알린다(6-2).
- 민감 열을 읽는 뷰를 찾아 운용자 조회 계정의 권한에서 뺀다(10-4).

## 8. 조회 (R4)

### 8-1. 행 조회

`POST /api/manage/tables/{table}/rows/query`(테이블 원본)와 `POST /api/manage/datasets/{dataset}/rows/query`(그래프가 실제로 보는 뷰).

```json
{ "filters": [ { "column": "severity", "op": "in", "value": ["critical", "major"] },
               { "column": "updated",  "op": "ge", "value": "2026-11-01" } ],
  "sort":    [ { "column": "updated", "dir": "desc" } ],
  "columns": ["id", "title", "severity", "updated"],
  "limit": 50, "cursor": null }
```

→ `{"columns": [{"name", "type"}], "rows": […], "next_cursor": "…" 또는 null, "total": n 또는 null, "changed": false}`. 값의 형식은 `/api/data`와 같다.

- 연산: `eq` `ne` `lt` `le` `gt` `ge` `in` `contains` `starts_with` `is_null` `not_null`. 유형에 맞지 않는 연산·값은 422 `invalid_filter`.
- 열 이름은 그 테이블의 열 목록과 대조한 뒤 `psycopg.sql.Identifier`로 넣고, 값은 전부 매개변수로 넣는다. 사용자 입력이 SQL 글에 들어가는 경로가 없다.
- 입력 폼의 참조 열(다른 테이블의 키 고르기)도 이 조회로 찾는다.
- **한 행 읽기:** 요청에 `"key": {"<기본 키 열>": <값>}`을 주면 그 한 행을 **자르지 않고** 돌려준다. 고치기 폼이 쓴다. 응답 한도(2MB)를 넘는 칸만 잘리고 `truncated_cells`에 적힌다.

### 8-2. 페이지 나눔 규칙

| 규칙 | 값 |
|---|---|
| 한 번에 돌려주는 행 | 기본 50, 최대 200. 서버가 강제한다(넘는 `limit`은 422) |
| 방식 | **커서**(정렬 열 + 기본 키의 다음 값부터). 깊은 페이지도 속도가 같다. 보장하는 것은 이만큼이다. **기본 키로 정렬하면**(기본) 첫 페이지를 받을 때 있던 행은 겹치거나 빠지지 않는다(기본 키는 바뀌지 않는다). 그 사이 더해진 행은 나올 수도 안 나올 수도 있다. **다른 열로 정렬하면**, 조회하는 사이 `update` 배치로 그 열의 값이 바뀐 행은 겹치거나 빠질 수 있다 |
| 고유한 키가 없는 조회 | 키 방식 커서는 행을 가리킬 고유한 키가 있을 때만 쓴다: 테이블, 그리고 원본 테이블의 기본 키 열을 모두 내보내는 `table:` 데이터셋. 그 밖의 데이터셋(`sql:` 뷰, 기본 키 열이 빠진 뷰)은 **건너뛸 행 수**로 넘긴다. 순서는 요청한 정렬 열 뒤에 나머지 모든 열을 붙여 고정한다(값이 완전히 같은 행끼리는 어느 것이 먼저 와도 결과가 같다). 깊이는 100,000행까지이고 넘으면 422로 조건을 좁히게 한다. 커서는 서버만 읽는 값이라 어느 방식이든 요청과 응답의 모양은 같다. 이 방식에서는 조회하는 사이 데이터가 바뀌면 행이 겹치거나 빠질 수 있고, 아래의 `changed`로 알린다. `dashboard.yaml`에 키를 적게 하지 않는다 |
| 조회 도중의 변경 | 커서에 첫 페이지 때의 **데이터 판**을 넣는다. 데이터 판은 그 테이블의 (마지막으로 다시 만든 시각 `load_snapshot.loaded_at`, 배치 기록의 이름·해시 목록을 합친 해시)다. 배치를 더하거나 빼면 뒤의 것이, 같은 이름의 파일 내용을 고쳐 apply하거나 `replace` 테이블의 CSV를 바꿔 apply하면 앞의 것이 달라진다. 데이터셋 조회는 그 뷰가 읽는 테이블들의 판을 합친다. 다음 페이지를 줄 때 지금 판과 다르면 응답의 `changed`가 `true`다. 화면은 "조회하는 사이 데이터가 바뀌었습니다. 처음부터 다시 보기"를 보인다. apply는 그 테이블이 실제로 안 바뀌었어도 판을 바꾼다(놓치는 것보다 한 번 더 알리는 쪽을 고른다). 서버가 여러 요청에 걸쳐 한 시점의 내용을 잡아 두지는 않는다(DB 접속을 붙잡게 된다). 내보내기는 쿼리 하나로 읽으므로 한 시점의 내용이다 |
| 전체 행 수 | **테이블과 `table:` 데이터셋**은 필터가 없으면 배치 기록에서 구한 행 수를 준다(세지 않는다. `table:` 데이터셋은 원본 테이블과 행이 같다). **`sql:` 데이터셋**은 조건·집계·조인으로 행 수가 원본과 다르므로 `null`이다. 필터가 있을 때도 `null`이고 화면은 "다음"만 보여 준다. 어느 경우든 `"count": true`를 보내면 그 조회의 결과 행을 100,000까지만 센다(넘으면 `"100000+"`) |
| 긴 값 | 목록에서는 셀 하나를 2,000자에서 자른다(`truncated_cells`로 알린다). 잘린 값은 보여 주기만 하고 저장에 쓰지 않는다. 전체 값은 한 행 읽기(8-1)로 받는다 |
| 시간 | `MANAGE_STATEMENT_TIMEOUT_MS`(기본 15000). 넘으면 504 `query_timeout` |

- 구현은 `dashkit/paging.py` 하나다(`limit` 검사, 커서 만들기·읽기, 키 방식과 건너뛰기 방식의 다음 페이지 조건 만들기). manager의 행 조회와 backend의 `/api/data`가 함께 쓴다.
- 운용 API의 작은 목록(테이블, 배치, 작업)은 기존 규칙(`{"items", "total"}`, `?page=&size=&sort=`)을 그대로 쓴다.

### 8-3. SQL 콘솔 (선택 `sql`)

`POST /api/manage/sql {"sql": "…", "limit": 50, "offset": 0}` → `{"columns", "rows", "has_more", "elapsed_ms"}`. 실행 한 번이 전부이고 저장하지 않는다.

- 접속 계정은 `dash_inspect`, 읽기 전용 트랜잭션, 시간 제한. 볼 수 있는 것은 `raw`·`dash`·`dashkit_meta`뿐이다.
- 서버가 `SELECT * FROM (<입력>) AS q LIMIT … OFFSET …`으로 감싼다. 문장 하나만 받는다. 감싸는 것만으로 SELECT가 아닌 문장과 쓰기 CTE가 문법 오류가 되고, 읽기 전용 계정과 읽기 전용 트랜잭션이 한 번 더 막는다.
- `limit` 최대 200, `offset` 최대 100,000. 전체 행 수는 세지 않고 한 행 더 읽어 `has_more`만 알린다.
- 실행마다 감사 로그에 남긴다(누가, 쿼리 글 앞 2,000자, 행 수, 걸린 시간).
- admin은 결과가 마음에 들면 그 SELECT 문으로 "데이터셋 만들기"(7-1)로 간다. 따로 저장 기능을 두지 않는다.

### 8-4. 내보내기 (선택 `export`)

`GET /api/manage/tables/{table}/export?format=csv`(필터는 8-1과 같다). 스트림으로 보내고 `EXPORT_MAX_ROWS`(기본 1,000,000)에서 끊으며 감사 로그에 남긴다.

### 8-5. 대시보드 쪽의 페이지 나눔

| 대상 | 지금 | 변경 |
|---|---|---|
| Superset 차트 | 집계 결과만 가져온다. 원본 행 수와 상관없다(`row_limit`) | 없음 |
| Superset 표 차트(원본 행 모드) | `row_limit`까지 한 번에 받는다(최대 50,000) | 선택. 차트 유형 레지스트리(`dashkit/charts/table.yaml`)에 `page_size` 필드를 더해 Superset의 서버 페이지 나눔을 켠다. **6.1.0에서 실측한 뒤** `superset-notes.md`에 적고 넣는다 |
| 웹앱 위젯(`/api/data/{dataset}`) | 최대 `DATA_MAX_ROWS`(5000)행, 넘으면 `truncated: true` | 선택 매개변수 `limit`·`cursor`를 더한다. 안 보내면 지금과 같다. 간트·칸반은 전체가 필요하므로 그대로 쓴다 |

## 9. 운용 화면

`web/admin/`에 메뉴를 더한다. 방식은 기존과 같다(바닐라 JS, 빌드 단계 없음, 문구는 `web/strings.js`, 인라인 스크립트 없음). manager가 떠 있지 않으면 데이터 메뉴는 보이지 않는다.

### 9-1. 메뉴

| 메뉴 | 내용 |
|---|---|
| **테이블**(`#tables`) | 목록: 이름, 방식, 행 수, 마지막 배치(시각·사람), 배치 수(많으면 "합치기 권장"), 쓰는 그래프 수. "여러 파일 올리기", "새 테이블"(admin) |
| 테이블 상세(`#table/<이름>`) | 위쪽에 **"추가"** 버튼(9-2). **미리보기**: 행 표, 열 머리글로 정렬, 열별 필터, 50행씩 다음·이전, 행마다 "이 행 고치기"(`update` 테이블) / **구조**: 열·유형·규칙·설명, "열 추가"(admin) / **배치**: 목록, 내려받기, 되돌리기, 뺀 배치 되살리기, 합치기(admin) / **쓰이는 곳**: 데이터셋 → 그래프 → 탭 |
| 새 테이블(admin) | CSV 놓기 → 추론 표(이름·유형·기본 키·참조를 고친다) → 방식·데이터셋·초안 그래프 선택 → 작업 진행 로그 |
| **데이터셋**(`#datasets`) | 목록(읽는 테이블, 쓰는 그래프 수), 행 미리보기, "데이터셋 만들기"(admin: 키와 SELECT 문) |
| **작업**(`#jobs`) | 도는 중이거나 끝난 적재·구조 변경 작업, 진행률, 로그, 빠진 행 내려받기 |
| **설정 이력**(admin) | 설정 변경 이력과 되돌리기, 설정 파일 내려받기 |
| 선택 기능의 화면 | **쿼리**(`#sql`), 테이블 상세의 **통계**(열별 빈 값 비율·고유값 수·최소·최대, 누를 때 계산)와 내보내기 버튼, **API 토큰**(admin). 켜진 기능만 보인다 |

데이터 쪽 동작은 기존 감사 로그 화면(`#audit`)에 함께 나온다. 동작 묶음 `data.`로 고른다.

### 9-2. 데이터 추가 화면 (R7)

들어가는 곳은 하나다: 테이블 상세의 **"추가"**. 방법을 탭 셋으로 고르고, 그 뒤의 미리보기·결과·취소는 같은 화면이다.

| 탭 | 화면 | 쉽게 하는 것 |
|---|---|---|
| **직접 입력** | `schema.yaml`에서 만든 폼. 열마다 한 칸 | 유형에 맞는 입력(목록에서 고르기, 달력, 체크, 숫자), 필수 표시, `default` 미리 채움, 열 설명을 도움말로, 참조 열은 대상 테이블에서 찾아 고르기. 칸을 떠날 때 형식을 검사하고 서버 오류는 그 칸 아래에 보인다. **"저장하고 계속"**(방금 값 유지를 고를 수 있다)으로 연달아 넣는다. 키보드만으로 끝까지 된다 |
| **여러 행** | 스키마의 열을 머리글로 한 표 | 엑셀·시트에서 복사해 **붙여넣기**(첫 줄이 머리글이면 저절로 맞춘다), 행 더하기·지우기, 칸마다 오류 표시. 500행을 넘으면 파일 탭으로 안내한다 |
| **파일** | 파일 놓기 | "빈 양식 내려받기"(머리글과 예시 한 줄). 놓으면 바로 미리보기가 돈다. 여러 개를 놓으면 한꺼번에 올린다 |

그 뒤는 같다.

1. **머리글 맞추기**(필요할 때만): 저절로 맞지 않은 머리글만 묻는다. 고를 수 있는 것은 있는 열, 버리기, (admin) 새 열로 추가. admin은 "다음에도 이렇게"를 켜 `aliases`에 저장한다.
2. **미리보기:** 행 수, 맞춰 준 것("CP949로 읽음", "날짜 형식 1,204개를 바꿈"), 더해지는 행·바뀌는 행·건너뛰는 행 수, 바뀌는 행의 전후 값(앞 20개), 오류(줄·열·이유, 파일이면 줄 번호로, 표면 그 칸에).
3. **고르기:** [넣기] · 오류가 있으면 [오류 행 빼고 넣기] · [취소]. 파일을 다시 올리지 않는다.
4. **진행:** 큰 파일은 진행률 막대. 화면을 떠나도 계속되고, 끝나면 운용 화면 위쪽에 알림이 뜬다.
5. **결과:** 들어간 행 수와 **[방금 추가 취소]**. 빠진 행이 있으면 [빠진 행 내려받기].

- **여러 파일 올리기**(테이블 목록): 파일 여러 개를 놓으면 파일과 테이블을 이름으로 짝지은 표를 보여 주고 사람이 고친다. 맞는 테이블이 없는 파일은 admin에게 "새 테이블로 만들기"를 제안한다. 미리보기는 전체를 한 번에 돌리고, 넣기도 전체가 한 단위다(5-2).
- 한 행을 넣든 백만 행을 넣든 이력에는 배치 한 줄로 남고, 방법이 함께 표시된다.
- `tokens` 기능이 켜져 있으면 테이블 상세에 "명령 복사"(그 테이블에 파일을 올리는 `curl` 예시)를 둔다.

### 9-3. 웹앱 쪽 (선택 `freshness`)

- 탭 머리에 "데이터 기준: <그 탭의 그래프가 읽는 테이블 중 가장 오래된 마지막 배치 시각>"을 보인다(`/api/app`의 탭에 `data_as_of` 추가. 배치 기록과 계보에서 계산한다).
- 테이블에 `freshness: 7d`처럼 기한을 두면, 넘겼을 때 운용 화면의 테이블 목록에 경고를 보인다.

### 9-4. 화면 코드의 구조

- 지금 `web/admin/admin.js`는 한 파일(715줄)에 메뉴 다섯(사용자, 그룹, 통계, 감사 로그, 테스트 메일함)이 들어 있다. 메뉴를 **모듈 하나씩**으로 나눈다: `web/admin/menus/<이름>.js`가 `{key, label, match, when, render}`를 내보내고 `admin.js`는 라우터와 메뉴 목록만 갖는다. 메뉴를 더하는 일은 파일 하나와 목록 한 줄이다. 기존 다섯도 같은 꼴로 옮긴다(동작은 바꾸지 않는다).
- **입력 부품은 열 유형에서 나온다.** `web/shared/fields.js`가 유형(`text`, `integer`, `number`, `boolean`, `date`, `timestamp`, `enum`)과 참조 열에 대한 입력 부품·형식 검사·표시 방법을 표 하나로 갖는다. 직접 입력 폼, 여러 행 표, 행 조회의 필터 입력, 추론 검토 표가 이것을 함께 쓴다. 테이블이나 열이 늘어도 화면 코드는 바뀌지 않고, 유형이 늘면 표 한 줄이다.
- Studio와 함께 쓰는 부품(DOM 도우미, 파일 놓기, 추론 검토 표, 작업 로그·진행률, 행 표)은 `web/shared/`에 한 벌만 둔다. 지금 `web/studio/dom.js`에 있는 것을 옮긴다. nginx와 studio 컨테이너가 각각 서빙한다(studio에 마운트 하나를 더한다).

## 10. 서비스 구성과 보안

### 10-1. 관리 서비스(manager)

```
브라우저 ── nginx(web) ─┬─ /api/…         → backend   읽기 전용. dash_reader, dash_auth                    (그대로)
                        └─ /api/manage/…  → manager   dash_owner, dash_inspect, dash_auth, Superset 관리자,
                                                      projects/ 쓰기                                        (신규)
Studio(127.0.0.1 전용, 인증 없음)                                                                           (그대로)
```

- 실행은 `python -m dashkit manage`, compose 서비스 `manager`(프로필 `manage`). 이미지는 Studio와 같은 것을 쓴다(`dashkit/Dockerfile`의 `studio` 단계. YAML을 고치는 데 `ruamel.yaml`이 필요하다).
- 웹앱과 같은 출처(`/api/manage/`)라 세션 쿠키가 그대로 온다. 로그인 확인은 `dashkit/auth`의 `require_operator`·`require_admin`을 그대로 쓴다.
- **backend에 넣지 않는 이유:** 모든 사용자가 닿는 서비스가 owner 계정과 Superset 관리자 계정을 갖게 된다. 따로 두면 보기 전용 배포에서는 manager를 빼면 되고, 큰 파일 적재가 대시보드 응답을 늦추지 않는다.
- manager 포트는 밖에 열지 않는다(nginx만 닿는다). **프로세스는 하나만 띄운다**(작업 상태와 미리보기한 파일 목록이 메모리에 있다).

### 10-2. 공용 코어: Studio와 manager는 로직을 갖지 않는다

Studio와 manager는 같은 일(추론, 파일 받기, 설정 연산, 저장, apply 실행)을 한다. 다른 것은 누가 부를 수 있는가뿐이다. 그래서 로직은 한 벌만 둔다.

| 위치 | 내용 | 쓰는 곳 |
|---|---|---|
| `dashkit/project/`(신규 자리) | 지금 `dashkit/studio/`에 있는 것을 옮긴다: 파일 저장·검증·원자적 교체(`store`), 변경 연산(`ops`), YAML 다시 쓰기(`yamledit`, `roundtrip`), 작업 실행기와 진행 로그(`jobs`), multipart 읽기(`upload`), 쓰기 잠금(`locks`, 10-3) | Studio, manager, CLI |
| `dashkit/ingest/`(신규) | 접수(`intake`: 파서·머리글 맞추기·`normalize`·정규형 쓰기), 한 줄씩 검증, `apply_batch`, `policies`, 배치 폴더와 기록(`batches`), 합치기 | 로더, manager, CLI, Studio |
| `dashkit/paging.py`(신규) | 8-2 | backend, manager |
| `dashkit/studio/app.py`, `dashkit/manage/app.py` | **라우팅뿐이다.** manager는 여기에 로그인 확인과 권한 판정을 더한다 | |

- 규칙: 두 앱 가운데 한쪽에만 있는 로직은 결함으로 본다. 같은 연산을 두 API로 실행했을 때 쓰인 파일이 바이트 단위로 같다는 테스트를 둔다.
- 옮기는 일은 동작을 바꾸지 않는다. `dashkit/studio/`의 기존 모듈 이름은 다시 내보내기로 남겨 기존 테스트가 그대로 통과해야 한다.
- 계약도 한 벌이다: 연산과 저장 방식은 `contracts/studio.md`, 추론은 `contracts/scaffold.md`를 그대로 쓰고, `contracts/manage.md`는 경로·권한·요청 보호만 적는다.

### 10-3. 동시 쓰기

쓰는 프로세스가 여럿이 된다(manager, Studio의 apply, `make apply`·`make ingest`). 지금의 프로세스 안 잠금으로는 서로를 막지 못하므로 **DB의 advisory lock**으로 바꾼다. 쓰는 쪽은 모두 DB에 접속하므로 따로 잠금 서버나 잠금 파일이 필요 없다(`dashkit/auth/store.py`가 이미 같은 방식을 쓴다).

**쓰기는 한 번에 하나다.** 잠금은 **데이터 DB에 하나**뿐인 쓰기 잠금이다. 프로젝트별 잠금도 테이블별 잠금도 두지 않는다. 데이터 DB에는 한 번에 한 프로젝트만 적재돼 있고 어느 프로젝트의 load든 같은 `raw`·`dash`를 통째로 바꾸므로(4-4), 잠금을 프로젝트마다 따로 두면 다른 프로젝트로의 전환과 지금 프로젝트의 적재가 서로를 막지 못한다. 배치 폴더나 `raw`를 바꾸는 모든 작업이 이 잠금을 잡는다: 더하기, 빠른 취소, 되돌리기·되살리기, 합치기, load·apply, 구조 변경.

- **왜 하나인가(규칙 검사):** `checks`는 여러 테이블을 읽을 수 있다. 서로 다른 테이블의 적재를 동시에 두면 각자의 검사가 상대의 커밋 전 행을 보지 못해 둘 다 통과하고, 합쳐진 상태가 규칙을 위반할 수 있다. 그러면 지금은 성공하고 다음 apply가 실패한다. 한 번에 하나면 검사는 언제나 앞선 작업이 커밋한 상태를 본다. 격리 수준은 기본(READ COMMITTED)으로 충분하다. 검사 문장이 잠금을 잡은 뒤에 실행되기 때문이다.
- **왜 하나인가(복구):** 살아 있는 작업은 모두 이 잠금을 잡고 있다. 그래서 잠금을 잡은 쪽이 보는 남은 묶음 기록은 전부 끊긴 작업의 것이다. 지금 도는 작업의 기록을 끊긴 것으로 잘못 볼 일이 없다.
- **잠금 밖에서 하는 일은 올린 내용만 보고 정해지는 것뿐이다**: 읽기, 머리글 맞추기, 값 다듬기와 검증, 정규형 쓰기, 해시 계산, 임시 테이블 채우기. 큰 파일에서 오래 걸리는 일이 이것들이다. **DB나 폴더의 상태를 보고 정하는 일은 모두 잠금 안에서 한다**: 설정 대조, 복구, 배치 파일 대조, 해시 중복 확인, 참조 대조, 기존 행과의 비교, 배치 번호 매기기, 반영, `checks`, 확정, 커밋. 잠금 밖에서 미리 본 상태는 잠금을 기다리는 사이에 낡을 수 있어서다. 잠금 안의 구간은 DB 안의 집합 연산이라 짧고, 그래서 큰 파일을 올리는 동안에도 다른 테이블의 한 행 입력이 그 파일을 읽는 시간을 기다리지 않는다.
- **잠금은 그 작업의 DB 접속에 묶인다**(세션 단위 `pg_advisory_lock`). 작업이 끝나면 풀고, 프로세스가 죽거나 접속이 끊기면 DB가 푼다. 복구는 제 트랜잭션으로 먼저 커밋하고 그 다음에 작업의 트랜잭션을 연다. 둘 다 같은 잠금 안이다.
- manager는 `MANAGE_LOCK_WAIT_MS`(기본 5000)까지 기다리고, 그래도 못 잡으면 409 `apply_running`으로 답한다(다시 만들기처럼 오래 잡는 작업이 도는 중이다). CLI는 `LOCK_TIMEOUT`까지 기다린다.
- **설정 파일:** DB를 건드리지 않는 저장(Studio의 탭 편집 등)은 이 잠금에 들어오지 않는다. 그래서 manager의 설정 변경은 `revision`을 반드시 받아 그 사이의 변경을 거절한다(6-3). 운영 서버의 같은 프로젝트 폴더에 Studio를 함께 띄우지 않는다.
- 그래프의 조회는 잠금과 상관없다. 적재는 커밋 전까지 보이지 않고, 다시 만드는 동안은 기다린다(15절).

**폴더를 바꾸는 작업의 공통 순서.** 더하기, 빠른 취소, 되돌리기·되살리기, 합치기는 모두 이 순서를 지킨다. `dashkit/ingest`의 함수 하나가 감싸고, 작업마다 따로 구현하지 않는다.

| 순서 | 내용 |
|---|---|
| 1. 잠금 | 쓰기 잠금을 잡는다. 더하기는 접수·검증·임시 테이블 채우기를 마친 뒤에 잡는다. **잠금을 잡을 때마다**(처음이든, 오류 뒤에 다시 잡든) **DB에 적재된 프로젝트가 이 작업의 프로젝트인지 본다**(`load_snapshot.project`). 다르면 그 사이 다른 프로젝트가 적용된 것이므로 409 `project_mismatch`로 거절한다(load·apply는 프로젝트를 바꾸는 작업이라 이 확인을 하지 않는다). **그리고 설정이 그대로인지 본다**: 접수·검증에 쓴 설정의 `revision`(6-3)이 지금 파일의 것과 다르면, 잠금을 풀고 지금 설정으로 접수·검증을 처음부터 다시 한다. 두 번 어긋나면 409 `stale_config`로 다시 시도하게 한다. **마지막으로, 지금 설정이 DB에 적용된 설정인지 본다**: 지금 파일의 데이터 설정 지문(4-4)이 스냅샷의 `data_revision`과 다르면 설정을 고치고 아직 apply하지 않은 것이므로 409 `rebuild_required`로 거절한다(load·apply와 구조 변경은 그 설정을 적용하는 작업이라 이 확인을 하지 않는다) |
| 2. 복구 | **지금 DB에 적재된 프로젝트의** 남은 묶음 기록을 처리한다(5-4, 5-6, 6-4). 이 잠금을 잡고 있으면 그 기록은 모두 주인이 없다. 다른 프로젝트 폴더의 묶음 기록과 파일은 건드리지 않는다. 그 프로젝트를 다시 load할 때 그 load가 처리한다 |
| 3. 대조 | **프로젝트의 모든 원본 데이터 파일**(누적 테이블의 배치들, `replace` 테이블의 CSV)의 이름과 해시를 배치 기록(`dashkit_meta.batch`)과 견준다. 바꾸려는 테이블만 보지 않는 이유: 참조 대조와 `checks`가 다른 테이블의 DB 내용을 읽으므로, 다른 테이블의 파일이 고쳐지고 apply되지 않았으면 지금은 통과하고 다음 apply에서 실패한다. 해시는 파일의 크기와 수정 시각이 지난번 확인 때와 같으면 다시 구하지 않는다. 다를 때의 처리는 아래 표 |
| 4. 작업 | 묶음 기록을 쓰고 파일과 DB를 바꾼다 |
| 5. 규칙 검사 | DB의 행이 바뀌었으면 같은 트랜잭션에서 프로젝트의 `checks`를 돌린다. 위반하면 DB와 파일을 모두 되돌린다 |
| 6. 마무리 | 커밋하고 묶음 기록을 지운 뒤 잠금을 풀고 `after_ingest` 훅을 부른다 |

대조에서 파일과 기록이 다를 때:

| 차이 | 더하기 | 빠른 취소 | 되돌리기·되살리기 | 합치기 |
|---|---|---|---|---|
| **바꾸려는 테이블**에 기록에 없는 **새 파일**만 있고, 그 번호가 기록의 모든 배치보다 뒤다 | 그 파일들을 번호순으로 먼저 반영한 뒤 진행한다 | 다시 만드는 길로 간다 | 진행한다(다시 만들면서 반영된다) | 거절(409 `rebuild_required`) |
| 바꾸려는 테이블에서 기록에 있는 파일이 **바뀌었거나 없어졌다**, 또는 새 파일의 번호가 기록의 배치보다 앞이다 | **거절**(409 `rebuild_required`) | 다시 만드는 길로 간다 | 진행한다 | 거절(409 `rebuild_required`) |
| **다른 테이블**의 파일이 기록과 다르다(새 파일, 바뀐 파일, 없어진 파일 어느 것이든. `replace` 테이블의 CSV를 고치고 apply하지 않은 경우가 여기다) | **거절**(409 `rebuild_required`) | 다시 만드는 길로 간다 | 진행한다 | 거절(409 `rebuild_required`) |

이미 반영한 배치 파일이 바뀌었거나 없어졌다는 것은 DB에 옛 행이 남아 있다는 뜻이다. 그 위에 더하면 파일에서 다시 만든 결과와 달라지므로, apply로 먼저 맞추게 한다.

- **커밋에 실패했거나 결과를 받지 못한 작업은 직접 뒷정리하지 않는다.** DB가 커밋을 끝냈는데 응답 전에 접속이 끊긴 경우와 정말 실패한 경우를 작업 쪽에서는 구분할 수 없다. 그래서 새 접속으로 잠금을 다시 잡고 **자기 묶음 기록에 대해 복구 절차를 그대로 돌린다**(5-4, 5-6, 6-4의 표). 복구는 배치 기록(`dashkit_meta.batch`)을 먼저 보고 판정하므로, 이미 커밋된 배치의 파일을 지우는 일이 없다. 작업은 복구의 결과로 답한다: 반영돼 있으면 성공, 치워졌으면 실패다. 묶음 기록이 이미 없으면 다른 프로세스가 복구한 것이므로 배치 기록을 보고 같은 방식으로 답한다. 파일을 지워도 되는지를 판정하는 곳은 복구 절차 하나뿐이다. **잠금을 다시 잡았을 때 DB에 다른 프로젝트가 적재돼 있으면 복구도 하지 않는다**(1번의 프로젝트 확인). 지금 DB의 배치 기록은 다른 프로젝트의 것이라, 그것으로 판정하면 이 프로젝트의 배치를 남의 테이블에 넣게 된다. 이때는 파일과 묶음 기록을 그대로 두고 409 `project_mismatch`로 답한다. 그 배치가 들어갈지는 이 프로젝트를 다시 load할 때 5-4의 표가 정한다(파일이 모두 제자리에 있으면 들어가고, 일부만 있으면 치워진다). 응답에 그렇게 적는다.
- 커밋한 뒤 묶음 기록을 지우기 전에 죽으면 기록만 남는다. 다음 복구가 지운다(5-4의 ①).

이 순서가 지키는 것은 하나다: **작업이 끝난 뒤 폴더의 파일로 다시 만든 결과가 지금 DB와 같다**(5-7). 1번의 설정 확인이 없으면, 고쳐 놓고 apply하지 않은 설정(예: 충돌 정책을 `skip`에서 `update`로)으로 새 배치만 넣게 되어 앞선 배치들은 옛 설정대로 남고, 잠금을 기다리는 사이 바뀐 규칙(`min`·`max`·`enum` 등은 DB 제약이 아니다)을 모른 채 옛 규칙으로 검증한 배치가 들어가 다음 apply에서 걸리고, 3번이 없으면 DB와 어긋난 파일 위에 작업이 쌓이고, 5번이 없으면 지금은 성공하고 다음 apply에서 실패하는 상태가 남는다.

### 10-4. 권한과 보호

| 할 수 있는 일 | admin | operator | user |
|---|---|---|---|
| 테이블·배치·데이터셋·계보 보기, 행 조회 | ✓ | ✓ | |
| 누적 테이블에 데이터 더하기(직접 입력·붙여넣기·파일·여러 파일, 미리보기, 오류 행 빼고 넣기) | ✓ | ✓ | |
| 머리글 맞추기(그 적재에만) | ✓ | ✓ | |
| 배치 되돌리기, 방금 추가 취소 | ✓ | 자기가 더한 배치만 | |
| SQL 콘솔, 내보내기, 통계(켜져 있을 때) | ✓ | ✓ | |
| 테이블 추가·삭제, 열 추가·변경(`aliases` 저장 포함), 데이터셋 만들기, 방식 변경, 합치기 | ✓ | | |
| 설정 되돌리기, API 토큰 | ✓ | | |

권한 검사는 서버에서 한다. 화면에서 버튼을 숨기는 것으로 끝내지 않는다.

- **요청 보호:** `dashkit/auth/guard.py`를 그대로 쓴다. 직접 입력·붙여넣기는 JSON이라 지금 규칙 그대로이고, 업로드 경로 셋(`…/tables/{t}/batches`, `/batches`, `…/tables/infer`)만 `multipart/form-data`도 받는다. 업로드 규칙(파일 이름, 크기)은 `contracts/studio.md`와 같다.
- **SQL:** 식별자는 목록과 대조한 뒤 `Identifier`, 값은 바인딩. 콘솔은 `dash_inspect` + 읽기 전용 트랜잭션 + 시간 제한.
- **경로 값:** `{table}`·`{dataset}`·`{file}`은 현재 프로젝트의 설정과 폴더 목록에 대조한 뒤에만 쓴다. 배치 파일 경로는 번호와 시각으로만 만든다.
- **감사 로그:** 기존 `dashkit_auth.audit_log`에 남긴다. 동작 코드: `data.batch.create`(배치 파일, 방법, 원래 파일 이름, 해시, 행 수)·`data.batch.failed`·`data.batch.remove`·`data.batch.restore`·`data.batch.compact`, `data.table.create`·`data.table.alter`·`data.table.drop`, `data.dataset.create`·`data.dataset.alter`, `data.config.restore`, `data.query.run`, `data.export`, `data.token.create`·`data.token.revoke`. 데이터 값은 남기지 않는다. 작업의 결과 요약도 여기에 남으므로 manager가 다시 떠도 이력에서 볼 수 있다.
- **민감 열(선택. 열에 `sensitive: true`를 적으면 켜진다):** 운용자에게 `raw` 조회를 열면 뷰에 내보내지 않던 값이 보인다. 화면이 아니라 **DB 권한으로** 막고, 그 값에 닿는 세 경로를 모두 막는다.
  - **원본 테이블:** 로더가 `dash_inspect`에게 그 열의 권한을 주지 않는다(PostgreSQL의 열 단위 권한). 행 조회와 내보내기는 그 열을 빼고 읽어 `***`로 표시하고, 콘솔에서 그 열을 읽는 쿼리(그 테이블의 `SELECT *` 포함)는 권한 오류가 된다.
  - **`table:` 데이터셋 뷰:** 민감 열을 **빼고** 만든다(`SELECT *`가 아니라 나머지 열을 적는다). 뷰는 소유자의 권한으로 원본을 읽기 때문에, 빼지 않으면 열 권한을 막아도 뷰로 읽힌다. 그 열을 그래프나 필터가 쓰고 있으면 지금의 열 참조 검사가 "뷰에 열이 없음"으로 알린다.
  - **`sql:` 데이터셋 뷰:** 로더가 계보의 열 단위 의존(7-2)으로 민감 열을 **어디서든 읽는 뷰와, 그 뷰를 읽는 뷰**를 찾아 `dash_inspect`에게 SELECT를 주지 않는다. 그 데이터셋의 행 조회는 403 `sensitive_dataset`, 콘솔은 권한 오류다. 조건절에만 쓰고 내보내지 않는 뷰도 막는다(틀린 허용보다 지나친 거절을 고른다). `dash_reader`의 권한은 바꾸지 않는다(그 값을 대시보드에 내보내는 것은 프로젝트를 쓴 사람의 결정이다). 대신 load가 "민감 열 `<테이블>.<열>`을 데이터셋 `<키>`가 읽음"을 경고로 알린다.
  - **검증 조건(테스트로 고정):** `sensitive` 열의 값을 `dash_inspect`로 ① `raw`에서 직접 ② `table:` 데이터셋 뷰로 ③ 그 열을 읽는 `sql:` 데이터셋 뷰와 그 위에 얹은 뷰로 ④ SQL 콘솔의 어떤 쿼리로도 읽을 수 없다. 그리고 적재 쪽 응답에서도 나오지 않는다: ⑤ 민감 열의 값이 틀려 난 오류 메시지 ⑥ **다른 열의 오류로** 빠진 행의 `rejects` 파일 ⑦ 미리보기의 전후 값 ⑧ 배치 파일 내려받기 ⑨ 작업 로그와 감사 로그.
  - **적재 쪽 응답:** DB 권한은 읽기 경로만 막는다. 적재는 owner 접속으로 돌고 올린 값을 다루므로, 응답을 만드는 곳에서 따로 가린다. 규칙은 하나다: **민감 열의 값은 운용 API의 어떤 응답에도 싣지 않는다.** 해당하는 곳은 미리보기의 전후 값(`changes`), 오류 메시지(값을 인용하지 않고 위치와 이유만 적는다. 예: `orders.csv:17:phone: 형식 불일치`), 빠진 행 내려받기(`rejects`. 그 열은 `***`), 배치 파일 내려받기(그 열은 `***`), 작업 로그, 감사 로그다. 가리는 일은 응답과 로그를 만드는 한 곳(`dashkit/ingest`의 결과 만들기)에서 하고 경로마다 따로 하지 않는다.
  - 그래서 민감 열이 있는 테이블은 빠진 행 파일만으로 다시 올릴 수 없다. 화면이 "가려진 열은 원래 파일에서 채워 주세요"를 알린다.
  - admin도 운용 화면에서는 보지 못한다(등급마다 계정을 나누지 않는다). 입력은 할 수 있다.
- 로그와 오류 응답에서 환경 변수의 비밀값을 가리는 규칙은 Studio의 apply와 같다.

### 10-5. API 토큰 (선택 `tokens`)

- admin이 운용 화면에서 만든다. 값은 만들 때 한 번만 보여 주고 DB(`dashkit_auth.api_tokens`)에는 SHA-256만 둔다. 이름, 허용 테이블 목록, 만료일, 마지막 사용 시각을 가진다.
- 할 수 있는 일은 **허용된 테이블에 데이터 더하기(JSON 행·파일)와 그 작업의 상태 보기**뿐이다.
- `Authorization: Bearer <토큰>`으로 보낸다. 세션 쿠키와 함께 오면 거절한다. 쿠키를 쓰지 않으므로 출처 검사 대상이 아니다.

### 10-6. 선택 기능을 켜는 방법

`MANAGE_FEATURES`(쉼표 구분, 기본 비어 있음)에 `sql`, `export`, `profile`, `freshness`, `tokens`를 적는다. 민감 열은 여기에 없다. DB 권한이므로 `schema.yaml`에 키가 있으면 언제나 적용된다. 꺼진 기능의 경로는 404 `not_found`이고, 운용 화면은 `GET /api/manage/config`의 `features`를 보고 메뉴를 그린다(테스트 메일함 메뉴가 메일 모드를 보는 것과 같은 방식).

## 11. API (`/api/manage`, 운용자만)

오류 형식과 공통 규칙은 `contracts/api.md`와 같다(`{"detail", "message"}`, 검증 오류는 `errors`, `Cache-Control: no-store`). 오래 걸리는 일은 202와 작업을 돌려주고 `GET /jobs/{id}`로 본다.

| 메서드·경로 | 내용 |
|---|---|
| `GET /config` | `{"project", "features": […], "limits": {…}}` |
| `GET /tables`, `GET /tables/{t}` | 목록(방식, 행 수, 마지막 배치, 배치 수, 쓰는 곳 수), 상세(열·규칙·`aliases`. 입력 폼이 이것으로 만들어진다) |
| `GET /tables/{t}/template` | 빈 양식(CSV: 머리글과 예시 한 줄) |
| `POST /tables/{t}/batches` | **데이터 더하기.** JSON `{rows, dry_run?, columns?}` → 200 결과(500행까지) · JSON `{upload_id, skip_invalid?, columns?}` → 202 작업 · multipart `file`, `dry_run?`, `force?`, `columns?`, `skip_invalid?`, `strict?` → 202 작업 |

## 12. 구성 변경

- **코드:** `dashkit/project/`(옮김, 잠금 추가), `dashkit/ingest/`(신규), `dashkit/manage/`(신규), `dashkit/paging.py`(신규), `dashkit/loader/`(누적 테이블을 배치 폴더에서 읽기, 배치 기록, 계보 기록, `dash_inspect` 권한), `dashkit/db.py`의 `inspect_conn()`, `dashkit/config.py`(새 키 검사), `dashkit/plan.py`(배치 단위 비교), `dashkit/scaffold.py`(원래 머리글을 `aliases`로), `web/admin/`(메뉴 모듈), `web/shared/`(공용 부품, `fields.js`).
- **로더의 변경 범위:** 통째로 다시 만드는 흐름은 그대로다. 달라지는 것은 누적 테이블의 행을 읽는 곳(파일 하나 → 정규형 배치 여러 개를 `apply_batch`로)과 기록에 적는 것뿐이다. `replace` 테이블의 경로와 값 검증의 엄격함은 건드리지 않는다(누적 테이블의 배치만 머리글의 부분집합을 받는다). 번들 스냅샷 테스트와 기존 로더 테스트가 바뀌지 않아야 한다.
- **의존성:** 새 패키지 없음. gzip은 표준 라이브러리, multipart는 기존 `upload.py`를 디스크로 받도록 넓힌다.

## 14. 단계와 완료 조건

| 단계 | 내용 | 완료 조건 |
|---|---|---|
| 1. 기반 | 계약 두 문서. 공용 코어로 옮기기(`dashkit/project/`, `web/shared/`, 운용 메뉴 모듈)와 DB 잠금. 접수(파서 둘, 머리글 맞추기, 값 다듬기, 정규형 쓰기), 한 줄씩 검증, `apply_batch`와 정책 표. `mode`·`on_conflict`·`default`·`aliases`와 배치 폴더를 읽는 로더, 배치 기록. `dash_inspect`. manager 골격과 로그인 확인 | 옮기기만으로는 동작이 바뀌지 않는다(기존 Studio·운용 화면 테스트 통과). 누적 테이블이 있는 프로젝트를 빈 DB에 `make apply`하면 같은 행이 된다. 기존 예시 3개의 번들 스냅샷과 테스트가 그대로 통과한다. 100만 행으로 apply 시간을 재어 15절에 적는다 |
| 2a. 더하기 | `POST /tables/{t}/batches`(JSON 행, 파일), 미리보기와 다시 올리지 않는 확정, 중복 감지, 이력, 되돌리기와 방금 추가 취소, CLI, `plan`의 배치 비교. 운용 화면의 테이블 목록, "추가"의 세 탭, 배치 | 한 행을 폼으로 넣고 "저장하고 계속"으로 이어 넣을 수 있다(키보드만으로). 같은 행들을 폼·붙여넣기·파일로 넣은 **배치 파일이 같다.** 올리면 sync 없이 그래프 값이 바뀐다. **하나씩 더한 결과와 처음부터 다시 만든 결과가 같다**(정책 셋, 빠른 취소 뒤에도). 실패한 것은 폴더에도 DB에도 남지 않는다. 확정 도중에 죽인 뒤 다시 띄우면 그 배치가 반영된다 |
| 2b. 대량 | 여러 파일 한 트랜잭션, 머리글 맞추기 화면과 `aliases` 저장, 오류 행 빼고 넣기와 빠진 행 내려받기, 진행률, 빈 양식 | 엑셀에서 CP949로 저장한 파일과 표시 이름 머리글의 파일이 손대지 않고 들어간다. 서로 참조하는 두 파일을 함께 올리면 둘 다 들어가거나 둘 다 안 들어간다(첫 파일만 옮긴 뒤 죽이고 다시 띄워도 그렇다). 200MB 파일을 미리보기한 뒤 다시 올리지 않고 넣는다. 서로 다른 프로세스의 적재와 apply가 순서를 지킨다 |
| 3. 조회 | 행 조회(커서), `dashkit/paging.py`, `/api/data`의 `limit`·`cursor`. 운용 화면의 미리보기와 데이터셋 목록, "이 행 고치기" | 100만 행 테이블에서 어느 페이지든 200행 이하로 온다. 필터·정렬 입력으로 SQL을 바꿀 수 없다(테스트) |
| 4. 구조 변경 | 테이블 추가, 열 추가·변경 연산, 데이터셋 만들기, 설정 변경 이력, 계보 기록과 "쓰이는 곳", 합치기 | 운용 화면만으로 새 CSV → 테이블 → 데이터셋 → 초안 그래프까지 간다. 열을 더하면 입력 폼과 데이터셋에 새 열이 보이고 기존 그래프는 그대로다. 같은 연산을 Studio와 manager로 실행한 파일이 같다. 합친 뒤 다시 만든 결과가 합치기 전과 같다 |
| 5. 선택 기능(첫 구현 범위가 아니다, D7) | SQL 콘솔, 내보내기, 통계, 민감 열, 신선도, API 토큰, 표 차트 `page_size`. 필요해진 것만, 각각 독립된 PR. 그 기능의 설정 키(`sensitive`, `freshness`)와 `MANAGE_FEATURES`도 그때 계약에 넣는다 | 꺼진 기능의 경로가 404다. 콘솔로 쓰기와 `dashkit_auth` 읽기가 안 된다. 토큰으로 조회·구조 변경이 안 된다 |

## 15. 위험과 한계

- **apply 시간이 누적 총량과 배치 수에 비례한다.** 다시 만들 때 모든 배치를 다시 검증하고 넣는다. 1차 목표는 누적 수백만 행이다(아래 "실측": 100만 행 33초, 같은 행을 배치 200개로 나누면 94초). 한 행씩 더한 작은 배치가 많으면 합치기로 줄인다(6-4). 그래도 느려지면 순서대로 넣는다: 검증 결과 캐시(테이블 정의와 파일 해시가 같으면 다시 검증하지 않는다), 바뀐 테이블만 다시 만들기. 그래도 안 되는 크기면 D1의 대안으로 간다.
- **다시 만드는 동안 그래프 조회가 기다린다.** `load`의 트랜잭션이 테이블을 잠그기 때문이고 지금도 같지만, 데이터가 크면 길어진다. 구조 변경, 빠른 길이 아닌 되돌리기가 여기에 해당한다. 일상의 추가 적재와 방금 추가 취소, 합치기는 조회를 막지 않는다.
- **값 다듬기는 사용자의 입력을 바꾼다.** 그래서 뜻이 하나뿐인 표기만 받고, 무엇을 몇 건 바꿨는지 미리보기에 보이며, 원래 파일은 남기지 않는다는 것을 화면에 적는다. 다듬기 규칙을 나중에 바꿔도 이미 저장한 배치는 정규형이라 영향이 없다.
- **저장 공간이 두 번 든다**(배치 파일 + DB). 배치는 gzip으로 저장해 줄인다. `update` 정책으로 같은 행을 여러 번 고친 테이블은 합치기 전까지 옛 판이 파일에 남는다.
- **큰 파일 하나는 한 번의 요청으로 올린다.** 중간에 끊기면 처음부터 다시 올린다. 나눠서 여러 파일로 올리는 것이 지금의 답이고, 이어 올리기는 후순위다.
- **`sql:` 데이터셋은 열 추가가 자동으로 보이지 않을 수 있다**(열을 하나씩 적은 쿼리). 작업 결과에 알린다.
- **큰 테이블의 필터·정렬은 느릴 수 있다.** 기본 키 정렬은 빠르지만 다른 열은 색인이 없으면 전체를 읽는다. 시간 제한에 걸리면 조건을 좁히라고 안내하고, 반복되면 색인 선언을 넣는다.
- **적재 중 `checks`는 프로젝트의 규칙 전부를 돈다.** 테이블이 커지면 한 행을 넣는 데도 그 시간이 든다. 그때 계보로 그 테이블과 이어진 규칙만 돌도록 좁힌다.
- **서버의 설정과 저장소가 어긋날 수 있다**(D4). 서버의 프로젝트 폴더가 운영의 기준이다. 저장소의 설정으로 덮어쓰기 전에 내려받아 합친다.
- **쓰기는 한 번에 하나다**(10-3). 잠금 안의 구간(비교 → 반영 → `checks` → 커밋)이 짧다는 전제다. 1단계 실측에서 100만 행 테이블에 1행을 더하는 잠금 구간이 0.3초, 1만 행은 1.0초, 1만 행 고치기는 1.7초였다. 큰 배치의 반영이나 무거운 `checks` 때문에 길어지면 그동안 다른 적재가 기다린다.
- **manager는 owner 계정과 Superset 관리자 계정을 갖고, 프로세스 하나로 돈다.** 포트를 밖에 열지 않고, 구조 변경은 admin만, 모든 쓰기를 감사 로그에 남긴다. 사내망에 열 때의 HTTPS 조건은 로그인 설계서 12절과 같다.
- **한 번에 한 프로젝트만 다룬다.** API 경로에 프로젝트 이름이 없다(backend와 같다). 여러 프로젝트 동시 운영(보강설계서 5-6)을 할 때 backend와 함께 경로가 바뀐다.
