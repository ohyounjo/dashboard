# Studio 미리보기 오류 조사 기록

이 기록은 이슈 #51의 진행 중인 조사다. 재현하지 못한 현상은 원인을 확정하지 않는다.

## 환경과 관찰

- 2026-11-21 격리 작업 폴더의 테스트 스택 `dashkit-test-2889489412`, 웹앱 `localhost:34120`, Superset `localhost:34128`, Studio `localhost:34129`; 테스트 전용 상태·볼륨 사용. Superset 공식 이미지 6.1.0, Playwright 1.65.1의 Chromium 159.0.8154.6 헤드리스, 새 브라우저 컨텍스트.
- 서비스워커: 수정 전 새 컨텍스트의 Superset 로그인 화면과 로그인한 웹앱의 Superset 임베드에서 `/static/service-worker.js` 등록이 404로 실패했다. 이미지의 SPA 템플릿은 해당 경로를 등록하지만 파일은 없었다. 등록 범위는 `/static/`; 기존 등록은 없었다. 임베드 페이지는 열렸으나 전체 차트 동작은 별도로 확인해야 한다. [Superset 이슈 #39431](https://github.com/apache/superset/issues/39431)에도 이미지 파일 누락이 보고됐다.
- 수정 후 동일 경로는 200, `application/javascript`이며 새 Chromium 컨텍스트에서 워커가 `/static/` 범위로 활성화됐다. 6.1.0 원본 워커의 install/activate 동작을 이미지에 해당 파일이 없을 때만 보충한다. 다른 Superset 버전으로 업그레이드하는 경로의 실측은 남았다.
- 수정 후 워커를 등록한 영속 Chromium 프로필을 종료하고 다시 열었을 때도 `/static/` 워커가 활성 상태였고 등록 오류는 없었다. 수정 전에 만들어진 등록이 남아 있는 프로필은 확보하지 못했다.
- 로그인 전: 새 세션에서 웹앱 `/api/app`이 401을 반환하고 `/login.html`로 이동했다. 인증 계약에 맞는 초기 접근이다. 로그인 요청은 200이었고 임베드 프레임이 생성됐다.
- 인증 없이 guest-token 요청은 401, Studio의 허용되지 않은 Host와 Origin은 각각 403이었다. Studio CSP의 `frame-src`는 테스트 웹앱을, 웹앱 CSP의 `frame-src`는 테스트 Superset을, 웹앱의 `frame-ancestors`는 테스트 Studio를 가리켰다. 이는 전체 권한 조합에 대한 검증은 아니다.
- Studio 요청 보호 회귀 테스트 76건과 일반 사용자·운용자 권한 및 허용되지 않은 대시보드의 guest token 거부를 포함한 접근 제어 통합 테스트 9건이 통과했다.
- 1280·390px 라이트/다크의 Studio 초기 화면을 각 한 번 확인했다. 1280px에서는 미리보기 프레임이 있고 390px에서는 보이지 않았으며 가로 오버플로가 없었다. 1280px 양쪽 테마에서 로그인 후 Studio → 웹앱 → Superset 프레임이 열렸다. 390px에서는 펼침 버튼과 미리보기 모두 CSS에서 숨겨져 있어 수동 펼침 검사를 할 수 없었다(설계의 예상과 다름). 대신 390px 양쪽 테마에서 별도 웹앱에 로그인하고 Superset 프레임이 열리는 것을 확인했다. `127.0.0.1` 출처에서 올바른 주소로 여는 안내 링크가 나타났다. 이 검사는 적용 후 모든 차트의 화면 확인을 대신하지 않는다.
- 차트 400과 404: 로그인한 1280px Chromium 중첩 미리보기에서 `devtracker` 적용, `sales-sample` 전환, `sales-sample` 재적용을 각 한 번 실행했다. sync의 prune은 각각 6·20·0개였고 세 적용이 성공했으며 최종 Superset 임베드 프레임이 열렸다. 수집한 차트·서비스워커·`/api/app` 관련 실패 요청은 없었다. 이 한정된 시도에서는 400과 404가 각각 재현되지 않았다. 수동 새로고침·차트 구성 변경 및 요청 시간 대조는 남았고 기존 iframe과 prune의 경쟁을 원인으로 확정하지 않았다.
- 추가 확인: 테스트 사본 `zz-preview-check`에서 차트 키 하나를 교체해 적용했을 때 기존 차트 1개가 prune됐고, 재적용에서는 0개가 삭제됐다. 각각 한 번 시도한 동안 차트 400·404는 관찰되지 않았다. 적용 로그 끝의 `done`을 브라우저 자동화로 제거한 시험에서는 상태 조회 후 실제 성공 결과와 로그가 복원됐다.
- 같은 브라우저 세션 시작 기준 최초 사본 적용은 3.8~10.2초, 차트 교체 적용은 15.2~18.3초, 재적용은 23.3~25.7초였다. 이후 32.1초에 의도적으로 지연한 차트 요청들의 취소를 관찰했고, 스트림 종료 시험은 38.1~40.9초였다. 각 적용 로그에는 check → load → sync → import → embed → prune 순서가 나타났다. 차트 오류가 발생하지 않아 오류 요청의 차트 ID와 sync의 경쟁 시점은 대조할 수 없다.
- 탐색 취소: 차트 데이터 요청을 자동화로 2.5초 지연시키고 미리보기를 연속으로 새로 고쳤을 때 요청 9건이 브라우저의 `net::ERR_ABORTED`로 취소됐다(HTTP 400·404 응답이 아님). 이후 화면에서 차트 9개와 값이 보였다. 인위적 지연 조건의 한 번의 재현이다.
- 설정 파일 오류와 잘못된 CSV를 테스트 사본에 넣었을 때 각각 `check`·`load` 실패가 화면과 작업 상태에 표시되고 마지막 성공 프로젝트가 유지됐다. 시험 후 원본 파일을 복구했다.
- 테스트 Superset 컨테이너를 중지한 상태에서 다른 사본을 적용하자 load 다음에 `sync` 실패가 표시되고 현재 프로젝트는 마지막 성공 프로젝트로 유지됐다. Superset을 다시 켜고 적용하자 새 프로젝트로 전환됐다. 이 시험의 실패 구간에도 계약에 명시된 DB와 이전 설정의 불일치 가능성은 남는다.
- 재적용 후 별도 웹앱을 1280·390px, 라이트·다크로 각각 열었을 때 4개 조건 모두 테스트 프로젝트의 네 탭이 표시됐다. 보이는 Superset 대시보드의 차트는 첫 탭 7개·마지막 탭 2개였고 두 위젯 탭에도 내용이 나타났으며, 확인한 화면에서 오류 문구는 없었다. 세션 쿠키는 `HttpOnly`, `SameSite=Lax`였다. 데이터 값의 정합성 전체를 대조한 것은 아니다.

## 남은 검증

차트 교체·삭제와 수동 새로고침의 반복 횟수 및 적용 중 요청의 세부 시각 대조는 제한적이다. 390px 수동 펼침은 현 UI에서 불가능하고, 수정 전부터 등록된 서비스워커가 남아 있는 프로필은 확보하지 못했다. 미완료 조건이 있으므로 구현 PR은 draft로 유지한다.
