# 병합 조합 통합 검증 설계

[이슈 #53](https://github.com/ohyounjo/dashboard/issues/53) · [PR #30](https://github.com/ohyounjo/dashboard/pull/30) · [PR #31](https://github.com/ohyounjo/dashboard/pull/31) · [실행 프롬프트](integration-verification-prompt.md)

## 목적과 기준

두 PR이 병합된 **최신 main의 같은 커밋**에서 단위·전체 테스트와 Studio 브라우저 흐름을 확인하고, 보강 보고서의 오래된 설명을 고친다. 이것은 검증 계획이며 아직 새 테스트를 실행했다는 뜻이 아니다. 시작할 때 이슈 본문·댓글과 최신 main을 다시 확인하고 커밋 SHA를 기록한다. 계약이 이슈와 다르면 계약을 기준으로 삼아 차이를 보고한다.

기준 문서는 `contracts/studio.md`의 요청 보호·미리보기, `contracts/auth.md`의 로그인, `contracts/chart-shorthand.md`의 중복 라벨 검사, `contracts/superset-notes.md` 13·14절이다. PR #29의 권한 실측과 PR #31의 검사 범위를 함께 확인한다. [이슈 #55](https://github.com/ohyounjo/dashboard/issues/55)는 같은 라벨의 서로 다른 지표가 조용히 제거되는 현상과 원본 유형 검사 보완을 별도로 다룬다. #53에서 이를 이미 해결됐다고 주장하거나 별도 이슈의 구현을 선행 조건으로 삼지 않는다.

## 실행 격리와 증거

1. 최신 `origin/main`에서 별도 worktree와 작업 브랜치를 만든다. 기존 worktree의 변경, `.env`, `.state`, `.build`, 프로젝트 데이터 및 다른 세션의 컨테이너·볼륨을 건드리지 않는다. 비밀값은 환경 변수로만 다루고 출력·커밋하지 않는다.
2. Makefile의 worktree별 `dashkit-test-<식별자>`, 포트, 이미지 접미사 및 `.test/` 경로와 `_guard_test`를 확인한다. 테스트가 `projects/zz-newtest`, `projects/zz-ingest`를 삭제·생성하므로 격리 worktree에 해당 경로가 없고 테스트 스택 이름·포트가 다른 실행과 겹치지 않는지 먼저 확인한다. 충돌하면 별도 포트 구간을 쓴다. 다른 실행의 스택을 내리지 않는다.
3. `make test-unit`과 `make test`를 실행하고 각 명령의 종료 코드, 통과·실패·skip 수, 실패 단계와 원인, 실행 SHA 및 환경을 기록한다. `make test`의 devtracker, Studio API, sales-sample, chart-gallery, 신규 초안, 누적 데이터 단계별 결과도 남긴다. `KEEP=1`을 쓰면 자신이 만든 스택인지 확인하고 브라우저 검증 후 같은 worktree에서 `make test-down`으로 정리한다. 실패 시 로그를 수집하고 비밀값을 제거한다.
4. `make test-unit`의 JS 단위 테스트와 `make test`의 Studio API 검사는 실제 iframe 로그인과 차트 렌더링의 증거가 아니다. 브라우저 검증을 별도로 수행한다. 수행 불가하면 사유와 미확인 항목을 기록하고 완료로 표시하지 않는다.

## 브라우저와 설정 검증

격리 스택에서만 실제 브라우저로 아래를 확인한다. 필요한 계정은 테스트 환경에서 생성하고 비밀값은 기록하지 않는다. 테스트 스택의 설정을 확인해 `STUDIO_ORIGIN`을 실제 테스트 Studio 출처에 맞춘다.

| 시나리오 | 기대 결과와 증거 |
|---|---|
| 허용된 Studio 출처의 미리보기 | Studio → 웹앱 로그인 → Superset 중첩 iframe에서 로그인 후 적용된 프로젝트의 대시보드와 차트가 보인다. 실제 화면과 관련 네트워크 결과를 기록한다. Studio에서 선택한 프로젝트가 아니라 `current`가 미리보기 대상이다. |
| 다른 출처 | 예를 들어 `localhost`와 `127.0.0.1`이 다른 경우 iframe 대신 올바른 Studio 주소 안내 및 링크가 표시된다. 계약의 Host 허용 조건을 함께 확인한다. |
| 차트 검사와 예시 | `devtracker`, `sales-sample`, `chart-gallery`의 check·apply 및 갤러리 조회 결과를 확인한다. 유효 예시가 거부되지 않는지, 별도 임시 사본에서 `bar`의 `x`와 `groupby` 중복이 YAML 경로가 있는 오류로 거부되는지 확인한다. 임시 사본은 테스트 공간에서만 만든다. |

브라우저의 오류·네트워크 실패를 맥락과 함께 기록하고, 기존에 관측된 인증 전 401이나 전환 중 요청 취소 등을 자동으로 회귀로 단정하지 않는다. 차트가 보였는지와 실패한 요청이 별개라는 점도 기록한다. 화면 크기나 브라우저 등 확인하지 않은 범위를 명시한다.

## 보고서 정정

`reference/enhancement-report.md` 7절을 중심으로 다음을 반영하고 실제 변경된 관련 문장도 대조한다.

- 현재 guest 권한은 그대로 세 개다. 기간 필터 변경에 필요한 이름은 `can_time_range on Api`, 세 원본 유형에 필요한 이름은 `can_explore_json on Superset`이다. PR #29의 실측 및 권고를 연결한다. 후자는 생성 SQL이 노출되는 제약이 있다. 권한을 늘리는 결정이나 구현은 이 이슈의 범위가 아니다.
- `x`와 `groupby`의 충돌은 PR #31의 검사 범위에서 적용 전에 보고된다. 실제 지원 범위와 아직 잡지 못하는 사례는 `contracts/superset-notes.md` 14절과 #55를 참조한다. 과거 단계의 관측을 수정할 때는 당시 관측과 현재 상태를 구별한다.
- 남아 있는 기간 필터·원본 차트 렌더링 제한, Studio 브라우저 접근성 등 다른 제한을 근거 없이 삭제하지 않는다.

## 회귀와 완료 판정

테스트 또는 실제 사용 흐름에서 병합 조합의 회귀가 발견되면 원인을 재현하고 수정한다. 영향받는 계약과 의미 있는 회귀 테스트를 함께 갱신하고 관련 검사와 두 전체 명령을 변경 후 다시 수행한다. 기존에 알려진 별도 이슈는 구별해 기록하며 완료 조건이나 범위가 바뀌면 #53을 갱신한다.

- [ ] 같은 최신 main 기준 SHA와 격리 조건, 두 테스트 명령의 결과·실패 원인을 기록했다.
- [ ] 브라우저 로그인 미리보기, 다른 출처 안내, 차트 검사와 세 예시 프로젝트를 검증했다.
- [ ] 보고서의 오래된 권한·실측·중복 라벨 설명을 고치고 남은 제한을 보존했다.
- [ ] 발견된 회귀를 수정하고 필요한 계약·테스트를 갱신했으며 변경 후 검증했다. 없으면 없다고 기록했다.
- [ ] 작업 결과 PR에 근거, 미확인 사항과 이슈 연결을 남겼다. 미완료 조건이 있으면 구체적으로 밝히고 완료로 주장하지 않는다.
